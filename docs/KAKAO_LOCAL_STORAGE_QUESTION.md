## 왜 묻는가

데브톡의 답변들은 **상업 서비스와 대량 수집을 전제로 한 것**이 많다.
우리 경우는 다르다.

- 개인이 쓰는 기록 도구다. 승인받은 몇 사람만 쓴다.
- **사용자가 검색 결과 중 하나를 직접 골라** 자기 기록에 붙인다.
- 장소 목록을 모으거나 재배포하거나 자체 장소 DB를 만들 뜻이 없다.

그 경우에 대한 답을 받고 나서 정한다. **짐작으로 기능을 뜯지 않고,
짐작으로 그대로 두지도 않는다.**

## 붙여넣을 본문

제목:

```
[이용정책 문의] 개인 기록 도구에서 사용자가 고른 장소 한 곳의 주소·좌표를 보관할 수 있는지 문의드립니다
```

본문:

```
안녕하세요. 개인용 독서·연구 기록 도구를 만들고 있습니다.
로컬 API 결과의 저장 범위에 대해 저희 경우를 적어 문의드립니다.

데브톡의 기존 답변들에서 "로컬 API 결과값은 어떠한 형태로든 저장할 수
없고 실시간 호출로만 이용할 수 있으며, 장소ID와 URL만 저장이 가능하다"는
내용을 확인했습니다. 저희 구조가 그 기준에 어긋나는지, 어긋난다면 어느
범위까지 허용되는지 확인하고자 합니다.

[서비스 성격]
- 개인이 읽은 자료와 그때 떠오른 생각을 기록하는 도구입니다.
- 현재 승인받은 이용자 3명만 쓰는 제한적 운영 단계입니다.
- 장소 정보를 모아 제공하거나 검색·추천하는 기능은 없습니다.
- 재판매, 재배포, 자체 장소 DB 구축 목적이 없습니다.

[이용 방식]
1. 이용자가 장소 이름을 입력하면 저희 서버가 로컬 API(키워드 검색)를
   호출합니다.
2. 결과 목록을 화면에 보여주고, 이용자가 그중 한 곳을 직접 선택합니다.
3. 선택한 한 곳을 "이 장소에 대한 내 메모"의 대상으로 기록에 붙입니다.
   이때 장소ID, place_url과 함께 도로명주소, 지번주소, 위경도, 카테고리,
   전화번호, 우편번호를 저장하고 있습니다.
4. 이후 그 기록을 열 때 저장된 주소를 글로 보여주고, 저장된 좌표로
   카카오맵 JS SDK 지도를 그려 위치를 표시합니다.
5. 지도의 저작권 표시는 건드리지 않습니다. SDK가 그리는 그대로 둡니다.

[문의]
(1) 위 3번에서 장소ID와 place_url 외의 값(주소, 위경도, 카테고리,
    전화번호, 우편번호)을 DB에 보관하는 것이 허용되지 않는 것으로
    이해하면 맞습니까?

(2) 허용되지 않는다면, 기록을 열 때마다 장소ID로 로컬 API를 실시간
    호출해 주소와 좌표를 받아 표시하는 방식은 괜찮습니까?
    (장소ID만 저장하고 나머지는 매번 조회)

(3) 이용자가 검색 결과를 쓰지 않고 주소를 직접 입력한 경우, 그 주소와
    좌표를 저장하는 것은 가능한 것으로 이해하면 맞습니까?

(4) 이미 저장되어 있는 기존 데이터는 어떻게 처리해야 합니까?
    (삭제, 또는 장소ID와 place_url만 남기고 나머지 삭제)

(5) 위경도를 저장할 수 없다면, 지도 표시를 위해 매번 장소ID로 조회하는
    것이 정상적인 사용 방식입니까? 아니면 지도 표시 자체를 다른 방식으로
    해야 합니까?

확정 답변을 받고 구조를 정하려고 합니다. 감사합니다.
```

## 함께 물어볼 수 있는 것

지금 글에는 넣지 않았다. **한 번에 여러 API를 묻으면 답이 뭉개진다.**

- **책 검색 API.** `book_profiles`에 출판사·ISBN·저자를 담고 있다.
  로컬 API와 다른 API이므로 따로 묻는다.
- **구글 지도.** 해외 장소도 같은 표에 주소와 좌표를 담는다. 구글은
  데브톡이 아니라 Maps Platform 약관을 글자로 확인해야 한다.
