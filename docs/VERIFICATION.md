# 검증 자산과 확인 결과

> 최종 확인: 2026-09-24 (태그 15-B, 웹사이트 15-C, 음악 15-D·15-E, 사용법 15-F, 쪽 넘는 인용 15-G)
> 대상: 인증·가입 승인 기반, Source·Capture·Project, Google Drive 연결과 파일 업로드,
> PDF 읽기·인용·페이지 메모·선택 문장 번역·파일 변경 감지 (1~13단계)

이 문서는 ThreadMark의 권한 통제를 **어떻게 다시 확인하는지**와 **무엇이 확인되었는지**를 기록한다.
기능을 추가한 뒤에는 아래 절차를 다시 실행해 통제가 여전히 유효한지 확인한다.

## 2. 데이터베이스 검증 (Supabase SQL Editor)

각 파일 전체를 SQL Editor에 붙여넣고 실행한다. 모두 읽기 전용이거나 스스로 되돌린다.

| 스크립트 | 확인 내용 | 판정 |
| --- | --- | --- |
| `supabase/verify/001_verify_auth_approval.sql` | 스키마·RLS·정책·함수·트리거·권한과 운영 상태 불변조건 | 23개 항목 표 |
| `supabase/verify/002_verify_first_admin.sql` | 관리자 부트스트랩 결과와 감사 트리거 동작 | 8개 항목 표 |
| `supabase/verify/003_rls_isolation_test.sql` | 실제 역할로 전환해 RLS와 가드 트리거가 막는지 | 68개 검사, 통과 메시지 또는 실패 지점 |

001의 검사 9(허용 목록 밖의 DEFINER 함수 없음)는 12-B 작업 중에 `soft_delete_capture`와
`soft_delete_project`가 목록에서 빠져 있는 것을 발견해 함께 채웠다. 10·11단계에서 추가된
함수인데 목록에 넣지 않아, 그대로 실행하면 그 검사는 실패했을 것이다.

Supabase SQL Editor는 스크립트 전체를 한 트랜잭션으로 실행한다. 그래서 앞선 검사에서
설정한 `request.jwt.claims`가 다음 검사까지 살아남는다. 자료를 만드는 검사는 삽입 전에
클레임을 비운다. 비우지 않으면 소유자 고정 트리거가 `owner_id`를 엉뚱한 사용자로 덮어쓴다.

003은 `authenticated`와 `anon` 역할로 실제 전환해 차단되어야 할 동작을 시도한다.
차단되지 않고 통과해 버린 변경은 블록이 예외를 일으키며 함께 되돌아간다.

## 3. 화면 흐름 확인 (수동)

두 번째 Google 계정이 필요하다. 시크릿 창을 사용한다.

| 확인 | 기대 동작 |
| --- | --- |
| 비로그인으로 `/home`, `/pending` 접근 | `/login`으로 이동 |
| 신규 로그인 (승인 모드) | `/pending` 도착, 상태는 `pending` |
| 승인 대기 상태로 `/home` 접근 | `/pending`으로 이동 |
| 관리자가 승인 | 대상이 재로그인 없이 `/home` 진입 |
| 관리자가 이용 정지 | 대상이 새로고침만으로 즉시 차단 |

### 좌표만 저장하지 않는다

설계 문서 9.3절이 직접 요구한 것이다.

> 위치 앵커는 페이지 + 선택 문장 + 주변 문맥 + 좌표 + 파일 checksum을
> 함께 저장한다. 좌표만 저장하지 않는다.

같은 절에 이유가 있다. 2단 편집을 가로질러 고르거나, 글꼴 인코딩이 비표준이거나,
수식·표·각주가 섞이면 좌표가 어긋난다. 단서를 여럿 남겨야 하나가 틀려도 되짚는다.

좌표는 픽셀이 아니라 **0~1 비율**로 담는다. (6.3절 마지막 줄) 픽셀로 담으면
확대율과 화면 크기에 묶여, 다른 기기에서 열면 엉뚱한 자리를 가리킨다.

### 6.3절 예시에 없는 항목 하나를 더했다

`sourceFileId`다. 한 자료에 PDF가 여럿일 수 있는데 예시의 항목만으로는 어느
파일인지 가릴 수 없다. `fileChecksum`은 "파일이 바뀌었나"를 보는 값이라(9.2절)
파일을 새로 올리면 값이 바뀌어 연결이 끊긴다.

### 원문은 고칠 수 없게 두었다

| --- | --- | --- |
| PDF에서 고른 문장 | `original_text` | **아니오** |
| 사용자가 쓴 메모 | `content` | 예 |

들어간 것이기 때문이다. 빈 줄이 있던 자리만 문단 구분으로 남긴다.

**줄 끝의 붙임표는 그대로 둔다.** 9.3절이 하이픈 처리를 오차가 생길 수 있는
경우로 꼽았다. `co-operate`처럼 원래 붙임표인 경우와 줄 끝에서 잘린 경우를
우리가 가릴 수 없다. 모르면 원문을 그대로 둔다.

이 스타일이 어긋나면 **보이는 것과 다른 문장이 잡힌다.** 눈으로는 알아채기
어렵고 기록에 남는 원문이 조용히 틀어진다. 그래서 `pdf-text-layer-css.test.mjs`가
원본과 같은지 확인한다. PDF.js를 올린 뒤 그 검사가 실패하면 손으로 고치지 말고
원본에서 다시 옮긴다.

### 페이지 메모를 함께 만든 이유

9.5절이 정한 안내문에 이런 구절이 있다.

> 페이지 메모는 사용할 수 있으며 OCR 기능은 추후 지원됩니다.

안내하게 된다. 그래서 `이 쪽에 메모`를 함께 만들었다.

페이지 메모의 locator는 `kind: "pdf-page"`이고 쪽 번호만 담는다. 고른 문장이
없으므로 문맥과 좌표도 없다. 없는 값을 빈 문자열로 채우지 않는다. 그러면

유형은 일반 메모이고 원문 칸은 비운다. 자료가 한 말이 없을 때 그 칸을 비워두는
것이 2.4절의 구분을 지키는 방식이다.

`trashed` 표시만 붙기 때문이다. 내용도 그대로 받아진다. 404가 나는 것은
영구 삭제된 뒤다.

본다. 상태는 `missing`으로 적되 사용자에게는 **휴지통이라고 알린다.**
복원하면 되는 일과 다시 올려야 하는 일은 다르기 때문이다. (10.4절)

Picker로 고를 때도 휴지통 파일을 막는다. Picker가 보여주지 않지만,

### 저자를 나눠 담는 이유

APA 7판은 영문 저자를 `Kim, D.`처럼 성과 이름을 갈라 적는다.

사람 이름은 규칙으로 가를 수 없다. 넣을 때 갈라 받아야 한다.

```
[{"family": "Kim", "given": "Daesoo"}, {"family": "한국교육과정평가원"}]
```

`given`이 없으면 그 이름을 그대로 쓴다. 기관 저자와 외자 이름이 그렇다.
기관을 위한 자리를 따로 만들지 않았다. "이름을 가를 수 없는 저자"는 기관이든
사람이든 다루는 방법이 같다.

입력은 한 줄에 한 사람이고, 쉼표가 있을 때만 가른다.
**쉼표가 없으면 추측하지 않는다.** 잘못 갈라놓은 이름은 참고문헌에 조용히
틀린 채로 실리고 사람이 알아채기 어렵다. 가르지 않은 이름은 눈에 띈다.

### 한국어 표기는 우리가 고른 것이다

설계 문서는 "APA 7판"까지만 정하고 한국어 논문의 표기는 정하지 않았다.
국내 학술지마다 관행이 조금씩 다르다. 지금은 이렇게 만든다.

```
김대수, 이서연 (2024). 학생의 오류에 대한 이해. 수학교육연구, 12(3), 45-67.
```

- 이름을 가르지 않고 그대로 적는다
- `&`를 쓰지 않고 쉼표로만 잇는다
- 쪽의 붙임표를 반각 대시로 바꾸지 않는다 (영문에서는 바꾼다)

**원문 언어를 모르면 영문 표기로 간다.** 둘 다 틀릴 수 있다면 고칠 엄두가
나는 쪽으로 틀린다. 한국어 이름에 영문 표기를 적용하면 `김, 대.`가 되어 더 나쁘다.

학회 양식과 다르면 `참고문헌 직접 쓰기`로 넘길 수 있다. 자주 어긋나면
`apa.ts`를 고친다. 그 파일 하나만 고치면 모든 참고문헌이 따라온다.

### 제목의 대소문자는 건드리지 않는다

APA는 제목에 문장형 대문자를 요구한다. 그런데 고유명사와 약어를 우리가
가려낼 수 없다. `PISA and TIMSS in Korea`를 `Pisa and timss in korea`로
바꿔놓으면 사람이 알아채기 어렵고, 알아채도 매번 고쳐야 한다. 적어준 그대로 둔다.

### 기울임을 넣지 않는다

APA는 학술지명과 권 번호를 기울여 쓴다. 우리는 글자만 돌려준다.
서식까지 담으면 붙여넣는 곳마다 다르게 깨진다. 기울임은 붙여넣은 곳에서 한다.

### 검사 대상 표가 4개뿐이었다

`tests/migration-invariants.test.mjs`의 `PROTECTED_TABLES`에 인증 관련 네 표만
들어 있었다. 그 뒤로 만든 `sources`·`captures`·`projects`·`source_files`는 검사
밖에 있었고, **새 표를 만들면서 RLS 켜는 것을 잊어도 아무도 말해주지 않는
상태였다.** 12개 전부로 넓혔다.

`google_drive_connections`는 조회 정책을 일부러 두지 않은 표다. "정책이 없다"와
"정책을 빠뜨렸다"는 화면에서 똑같아 보이므로, 어느 쪽인지를 목록에 적어 구분하고
그 표에는 권한 자체가 없는지를 대신 확인한다.

Crossref가 초록을 안 주는 일이 잦은데, 그때 적어둔 초록이 지워지면
사용자는 이 기능을 다시 쓰지 않는다. 가져오기가 무언가를 지우는 일은 없다.

제목은 `sources`가 주인이라 바로 바꾸지 않는다. 가져온 제목이 다르면
"제목도 바꿀까요"를 눈에 보이게 묻고, 답해야만 움직인다.

### AI에게 보내기 전에 보여준다

설계 문서 18절: "요청 전에 전송될 텍스트 범위를 사용자가 확인할 수 있게 한다."

그래서 두 걸음이다. `AI로 읽기`는 PDF에서 글을 꺼내 보여주기만 하고
아무것도 보내지 않는다. `AI에게 보내기`를 눌러야 나간다.
덤으로, 스캔본이라 글자가 없다는 것을 돈을 쓰기 전에 알게 된다.

### 지어내지 못하게 세 겹으로 막았다

1. 지시문에서 "글에 없는 것은 비워 둔다. 짐작해서 채우지 않는다."
   "참고문헌 목록에 있는 다른 논문의 정보를 가져오지 않는다."
2. **DOI는 받지 않는다.** 여기까지 왔다는 것은 DOI를 못 찾았다는 뜻이고,
   그 상황에서 모델이 내놓는 DOI는 지어낸 것일 가능성이 높다.
   지어낸 DOI는 엉뚱한 논문을 가리킨다. 서지 정보에서 가장 나쁜 실패다.
3. 연도는 범위를 확인한다. 쪽 번호를 연도로 잘못 볼 수 있다.

화면도 출처에 따라 색을 달리한다. Crossref는 초록, AI는 노랑이다.
같은 얼굴로 보여주면 둘 다 대충 보게 된다.

대신 화면이 그 상태를 **보여준다.** 연결이 없고 계획만 남은 프로젝트도 목록에
띄우고, "연결은 끊겼고 계획은 남아 있다"를 알린다. 감추면 사라진 것과 구별할
방법이 없다. 13-D의 보안 원칙 6과 같은 생각이다.

이 경우는 **아직 눌러보지 않았다.** 계획을 적은 뒤 프로젝트 연결을 끊고 그 안내가
뜨는지 확인한다. 조회는 연결을 걸러내지 않으므로 코드상으로는 남지만, 안내가
실제로 보이는지는 화면에서만 알 수 있다.

### 연결 표라서 양쪽을 따로 검사한다

이 표는 논문과 프로젝트 두 곳을 가리킨다. 외래키 제약은 RLS를 보지 않으므로
한쪽만 확인하면 다음이 가능해진다.

| 시도 | 막지 않으면 |
| --- | --- |
| 내 프로젝트 + 남의 논문 | 남의 논문을 내 프로젝트에 편입 |
| 남의 프로젝트 + 내 논문 | 남의 프로젝트에 내 계획을 밀어넣음 |

003의 검사 58과 59가 각각 한 방향씩이다. 검사 60은 **자기 것끼리는 열려야
한다**를 확인한다. 양쪽을 확인하는 트리거가 지나치면 정상적인 연결까지 막는데,
그러면 기능 자체가 성립하지 않는다. 검사 61은 짝을 나중에 바꿀 수 없는지 본다.

### 지우기는 두 번 눌러야 한다

### 색을 사람마다 고르게 한 방법

핵심은 CSS 한 낱말이었다.

```css
@theme inline { ... }   /* 색이 클래스에 박혀 바꿀 수 없다 */
@theme { ... }          /* 클래스가 변수를 가리켜 바꿀 수 있다 */
```

`inline`을 떼자 `<html data-palette="moss">` 하나로 앱 전체 색이 바뀐다.
화면 서른 곳의 `bg-zinc-50`은 그대로 두고, `zinc`가 가리키는 값만 갈래마다
다르게 둔다. 검사가 `@theme inline`이 다시 들어오는 것을 막는다.

### 밝기를 색보다 먼저 묻는다

색 갈래 셋이 모두 밝은 화면으로 만든 것이라, 컴퓨터가 어두운 모드면 무엇을
골라도 비슷해 보인다. 밝기를 먼저 정해야 색을 고른 결과가 보인다.

Tailwind의 `dark:`는 원래 컴퓨터 설정만 본다. `@custom-variant`로 다시 정해
세 상태를 모두 다룬다. `:not([data-mode="light"])`가 빠지면 `밝게`를 골라도
컴퓨터가 어두울 때 어두운 쪽이 함께 걸린다. **고르는 칸은 있는데 아무 일도
일어나지 않는** 상태이고, 원인을 찾기 어렵다. 검사가 붙어 있다.

`color-scheme`도 함께 바꾼다. 빼면 바탕만 어두워지고 스크롤 막대와 라디오
단추는 밝은 채로 남아 화면이 반씩 갈라진다.

### 어두울 때 카드가 바탕보다 어두웠다

처음에 반대로 만들었다. 어두운 화면에서 위로 떠 있는 것은 더 밝아야 떠 보인다.
카드가 바탕보다 어두우면 파인 것처럼 보인다. 세 갈래 모두 그랬다.

검사가 두 값의 밝기를 견준다. 나중에 색을 손볼 때 뒤집히면 바로 잡힌다.

### 값 목록이 세 곳에 있다

`theme.ts`, 마이그레이션의 `check` 제약, `globals.css`의 규칙이다.
어긋나는 방향마다 증상이 다르다.

| 어디에만 있나 | 증상 |
| --- | --- |
| 목록에만 | 고를 수는 있는데 저장이 거부된다 |
| 제약에만 | 아무도 고를 수 없는 값이 남는다 |
| CSS가 빠지면 | 저장은 되는데 화면이 그대로다 |

마지막이 가장 나쁘다. 저장했다는 말을 보고 화면을 보는데 아무것도 달라지지
않는다. 고장인지 원래 그런 것인지 알 수 없다. 검사가 셋을 맞대어 본다.

### 여기는 열거형을 쓰지 않았다

`text` + `check`다. 다른 곳과 다른 선택이라 이유를 남긴다. 열거형은 한 번 만든
값을 **지울 수 없는데** 디자인은 바뀐다. 갈래를 빼거나 이름을 바꾸는 일이 실제로
생기고, 그때마다 쓰지 않는 값이 영원히 남는다.

자료 상태나 관계 종류와 성격이 다르다. 그것들은 뜻이 정해진 값이고 틀리면
기능이 어긋난다. 화면 취향은 틀려도 기본 모양으로 보이면 그만이다.

### 모든 화면이 서버 화면이 되었다

뿌리 레이아웃이 취향을 읽으면서 `/`와 `/_not-found`까지 서버에서 그린다.
이 앱은 어차피 모든 화면이 사람마다 다르므로 잃는 것이 없다. 취향을 브라우저에서
붙이면 첫 그림이 기본 색으로 나왔다가 바뀌어 깜빡인다.

### 전문 검색이 아니라 글자 포함 검색이다

PostgreSQL의 전문 검색은 말을 토막 내고 어간을 찾아 견준다. 그 사전이 영어에는
있고 **한국어에는 없다.** 사전 없이 돌리면 띄어쓰기로만 토막 나서 `모델링`으로
`수학적모델링`을 찾지 못한다. 글자 포함 검색은 붙여 쓰든 띄어 쓰든 찾는다.

대가는 속도다. 색인을 타지 못하고 줄을 하나씩 본다. 개인이 쌓는 양에서는 문제가
되지 않고, 느려지면 그때 `pg_trgm` 색인을 건다.

### 검색어의 특수 문자가 조용히 결과를 바꾼다

여기서 틀리면 **오류가 나지 않고 결과만 틀린다.** 화면은 멀쩡히 목록을 보여주는데
있어야 할 것이 없다. 사용자는 검색이 잘못됐다고 생각하지 않고 "그런 자료가 없나
보다" 하고 넘어간다. 그래서 글자마다 검사를 붙였다.

| 글자 | 막지 않으면 |
| --- | --- |
| `%` | "아무 글자나"로 읽혀 `50%`가 `50`으로 시작하는 것을 전부 끌어온다 |
| `_` | "한 글자"로 읽혀 `source_id`가 `sourceXid`도 찾는다 |
| `,` | PostgREST에서 조건을 가르는 표시다. `Blum, W.`가 두 조건으로 쪼개진다 |
| `"` | 값을 감싼 따옴표를 깨뜨린다 |

**막는 순서가 중요하다.** 무늬를 먼저 만들고(`%` 막기) 그다음에 감싼다. 반대로
하면 무늬를 만들며 넣은 `\`가 감싸는 쪽에서 다시 먹혀 사라지고, 퍼센트가 다시
"아무 글자나"로 살아난다. 검사 하나가 그 순서를 붙잡고 있다.

참고문헌을 그대로 붙여넣는 일이 잦아서 쉼표는 실제로 만나는 경우다.

### 찾는 자리

자료는 제목·부제·설명, 기록은 적은 글·원문·번역문이다. 논문의 **저자와 학술지는
아직 찾지 못한다.** 저자가 jsonb라 PostgREST로 글자 견주기를 걸 수 없고, 데이터베이스
함수나 생성 열이 필요하다. 필요해지면 그때 만든다.

삭제 표시된 자료에 딸린 기록은 결과에서 뺀다. 자료 목록에서 사라진 것이 검색에만
나오면 눌러도 갈 데가 없는 줄이 된다. 자료에 붙지 않은 독립 기록은 그대로 보여준다.

### 찾기는 메뉴가 아니라 창이다

매일 여러 번 쓰는 일이라 화면을 한 번 거쳐 가게 하면 그만큼 덜 쓰게 된다.
머리말에 창을 두었다. 좁은 화면에서는 로고와 메뉴 넷과 설정이 이미 한 줄을
채우고 있어서 창을 접고 `찾기` 글자로 바꾼다.

검색어는 주소에 남는다. 새로고침해도 결과가 그대로이고 자주 쓰는 검색은
즐겨찾기에 담을 수 있다.

## 4-18. 2026-09-24 배포에서만 PDF를 읽지 못했다

로컬에서 멀쩡하던 `PDF에서 DOI 찾기`와 `AI로 읽기`가 배포에서만
"PDF를 읽지 못했습니다"로 끝났다. 사용자가 실제 논문을 담다가 발견했다.

### 원인은 올라가지 않은 파일 하나였다

`serverExternalPackages`는 "묶지 말고 `node_modules`에서 가져다 써라"는 뜻이다.
로컬에는 `node_modules`가 통째로 있으니 잘 돈다. 배포에는 **필요하다고 추적된
파일만 올라간다.**

pdf.js는 Node에서 진짜 worker를 띄우지 않는 대신 `GlobalWorkerOptions.workerSrc`를
`./pdf.worker.mjs`로 잡고 그 파일을 불러온다. 그 경로는 실행 중에 만들어지는
문자열이라 추적기가 따라가지 못한다.

```text
전:  pdfjs-dist/legacy/build/pdf.mjs                     ← 이것만 올라감
후:  pdfjs-dist/legacy/build/pdf.mjs + pdf.worker.mjs
```

확인은 `.next/server/app/(app)/sources/[id]/paper/page.js.nft.json`을 열어
`pdf.worker.mjs`가 있는지 보면 된다. Vercel이 올릴 파일을 정하는 것이 그 파일이다.

### 2026-09-23의 그것과 문구는 같고 원인은 다르다

둘 다 "PDF를 읽지 못했습니다"다. 그때는 묶여서 깨졌고 이번에는 안 올라가서
깨졌다. 그때는 로컬에서도 실패했고 이번에는 **로컬에서 멀쩡했다.**
로컬에서 아무리 돌려봐도 보이지 않는 종류다.

### 고치는 중에 한 번 더 헛디뎠다

`outputFileTracingIncludes`의 열쇠는 경로가 아니라 **글로브 무늬**다.
`[id]`를 그대로 적으면 "i 또는 d 한 글자"라는 뜻이 되어 우리 경로에 맞지 않는다.
맞지 않아도 오류가 나지 않는다. 설정은 있는데 아무 일도 하지 않고 빌드는
통과한다. 빌드 결과를 열어보고서야 알았다.

`tests/pdf-server-config.test.mjs`가 넷을 붙잡는다. 그중 하나는 빌드 결과의
추적 파일을 직접 열어 본다. 빌드하지 않았으면 건너뛴다.

### 아직 확인하지 않았다

로컬에서는 원래 되던 것이라 여기서는 차이가 보이지 않는다.
**배포한 뒤 실제 논문으로 확인해야 한다.**

## 4-19. 2026-09-24 프로젝트를 연결하면 흰 화면이 떴다

사용자가 논문에 프로젝트를 연결할 때마다 `This page couldn't load`가 떴다.
새로고침하면 연결은 되어 있었다.

### 서버 로그가 비어 있는 것이 단서였다

Vercel 로그를 열어보니 그 시각의 요청이 **전부 200**이었다. 500이 하나도 없다.
서버는 제 할 일을 다 한 것이다. 그러면 터진 곳은 브라우저다.

| 본 것 | 가리키는 곳 |
| --- | --- |
| 연결은 저장되어 있다 | 동작은 성공 |
| 새로고침하면 멀쩡하다 | 화면 코드 자체는 성하다 |
| 서버 로그에 500이 없다 | 서버가 아니다 |
| 논문에서만 난다 | 논문에만 있는 칸이 있다 |

넷을 겹치면 한 곳만 남는다. 논문에만 있고, 다시 그리면 괜찮아지는 것.
**활용 계획 칸이다.**

### 그릴 때 한 번 만든 상태

그 칸은 프로젝트 목록을 받아 **처음 그려질 때 한 번** 상태를 만들었다.
연결이 끝나면 서버가 프로젝트가 하나 늘어난 목록을 보내는데, 칸은 이미
그려져 있어서 처음 만든 상태를 그대로 들고 있다. 새 프로젝트의 상태가
없으니 없는 값을 건드린다.

붙잡을 것은 **사용자가 고친 것**뿐이다. 상태를 비워두고 손대지 않은 칸은
그때그때 서버가 보낸 값에서 만든다. 목록이 늘든 줄든 어긋날 자리가 없다.

같은 실수가 다른 화면에도 있는지 찾아봤다. 분석 서식은 안전하다. 그 열쇠는
고정된 서른 칸에서 오고 읽을 때도 받쳐둔다. **열쇠가 서버가 보낸 목록에서
올 때만** 생기는 문제다. AGENTS.md 6절에 남겼다.

## 4-20. 2026-09-24 아이패드에서만 문장을 드래그할 수 없었다

| 기기 | 결과 |
| --- | --- |
| 데스크톱 (엣지) | 됨 |
| 안드로이드 폰 | 됨. 길게 눌러 범위를 잡으면 기록으로 넘어간다 |
| 아이패드 (사파리) | **안 됨** |

### 화면에 이유를 적게 한 것이 답을 줬다

처음에는 "이 PDF에서는 선택 가능한 텍스트를 찾지 못했습니다"만 떴다. 그 문구는
글자가 정말 없는 스캔본과, 글자를 꺼내다 실패한 경우에 똑같이 떴다. 실패 이유는
삼키고 있었다. 아이패드에는 콘솔을 붙일 수 없어 알아낼 방법이 없었다.

둘을 가르고 이유를 화면에 적게 했더니 이렇게 나왔다.

```text
undefined is not a function (near '...t of e...')
```

사파리가 `for ... of`로 반복할 수 없는 것을 반복하려 할 때 내는 말이다.

### 사파리는 스트림을 `for await`로 읽지 못한다

pdf.js의 `getTextContent()`가 이렇게 되어 있다.

```js
const readableStream = this.streamTextContent(params);
for await (const value of readableStream) { ... }
```

`ReadableStream`의 비동기 반복은 규격에 있는데 **사파리에 구현이 없다.**
크롬·파이어폭스는 있다. 기기별 차이와 정확히 맞는다.

### 한 줄을 피해 가지 않고 기능을 채웠다

pdf.js 안에 같은 방식으로 읽는 곳이 하나 더 있다. 한 곳을 피하면 다른 곳에서
다시 만나고, 라이브러리를 올릴 때마다 새로 생길 수 있다. 빠진 것이 규격에 있는
기능이므로 **없을 때만** 채워 넣는다. 사파리가 나중에 지원하면 그쪽이 쓰인다.

잘못 채우면 증상이 고약하다. 글자를 꺼내다 중간에 멈추거나, 스트림을 쥔 채
놓지 않아 다음 쪽을 읽지 못한다. 둘 다 오류 없이 조용히 일어난다. 그래서
끝까지 읽는지, 다 읽고 놓는지, 중간에 그만두면 취소하는지를 검사로 붙잡았다.

### 확인했다

배포 뒤 아이패드에서 문장을 길게 눌러 범위를 잡으면 기록으로 넘어간다.
데스크톱과 안드로이드는 원래대로다.

## 4-21. 2026-09-24 읽는 자리를 넓히고 분석 탭에서 빈칸을 감췄다

논문을 실제로 검토하던 사용자가 "논문 화면과 옆 기록 화면의 세로가 작다"고 했다.

### 머리말 세 줄을 한 줄로

읽기 화면은 창 높이를 재서 남는 만큼을 PDF에 준다. (`fill-viewport.tsx`)
그래서 **위에서 줄인 만큼이 그대로 읽는 자리가 된다.**

| 예전 | 지금 |
| --- | --- |
| `← 자료 제목 / 파일명 4.6MB` | 한 줄로 합침 |
| 파일 고르는 칩 줄 | `← 제목 [파일A][파일B] 4.6MB [파일 확인] 13:36` |
| `파일 확인` 단추 + 마지막 확인 줄 | |
| PDF 아래 세 줄짜리 안내문 | 없앰 |

100픽셀쯤 늘었다. `파일 확인`은 **알릴 것이 있을 때만** 줄을 하나 더 쓴다.
확인하는 수단 자체는 없애지 않았다. 없애면 "방금 Drive에서 지웠는데 아직
멀쩡해 보이는" 경우를 확인할 길이 사라진다. (13-D에서 정한 것)

제목과 파일 이름은 자른다. 줄이 늘면 아래가 줄어드는 화면이라 길이를 예측할
수 있는 편이 낫다. 전체 이름은 마우스를 올리면 보인다.

없앤 안내문의 "드래그하면 인용" 이야기는 오른쪽 `메모` 탭이 이미 하고 있었다.
방향키 이야기는 도구 줄 오른쪽 끝으로 옮겼다. 제 줄을 쓰지 않는 자리다.

### 분석 탭에서 적은 것만 보기

서른 칸 중 일곱을 적었을 때, 적은 것을 다시 읽으려면 빈칸 스물셋을 지나야
했다. 빈칸을 감추는 전환을 두었다. 감추면 적은 것이 자연스럽게 위쪽에 모인다.

**순서는 바꾸지 않는다.** 8.2절의 차례는 논문을 읽는 순서라, 채운 것을 위로
끌어올리면 무엇을 적다 말았는지 알 수 없어진다. 빼기만 한다.

읽기 전용 복사본을 위에 붙이는 방식은 쓰지 않았다. 같은 내용이 화면에 두
벌이 되면 어느 쪽을 고쳐야 하는지 헷갈린다. 사용자도 "기록 탭에 섞으면
난잡해질 것 같다"고 했다.

한 번 켜면 이 브라우저에 기억한다. 논문마다 다시 누르게 하면 있으나 마나다.
갈라진 너비를 기억하는 것과 같은 방식이다. (`split-pane.tsx`)
켜둔 채로 아무것도 안 적은 논문을 열면 칸이 어디 갔는지 알 수 있게 안내한다.

## 4-22. 2026-09-24 확인 결과 (17-A 계정과 자료 지우기)

### 지우는 질의를 표마다 쓰지 않았다

만들기 전에 마이그레이션 29개의 외래키를 전부 훑었다. 자료를 담는 표가 하나도
빠짐없이 `auth.users`를 `on delete cascade`로 물고 있었다. `sources`,
`captures`, `projects`, `capture_projects`, `source_projects`, `source_files`,
`paper_profiles`, `paper_analyses`, `paper_project_uses`, `source_relations`,
`tags`, `source_tags`, `capture_tags`, `website_profiles`, `music_profiles`,
`music_provider_links`, `google_drive_connections`, `profiles`.

그래서 **계정 행 하나를 지우면 끝난다.** 표를 하나씩 지우는 코드가 더 꼼꼼해
보이지만 실제로는 반대다. 표가 늘어날 때마다 그 파일에 줄을 더해야 하고,
더하지 않아도 아무 일이 일어나지 않는다. **빠뜨려도 드러나지 않는 방식은
반드시 빠뜨린다.** 데이터베이스가 이미 아는 것을 코드가 다시 적지 않는다.

일부러 남기는 것은 셋이고 모두 `on delete set null`이다.
`admin_audit_logs.actor_id`, `admin_audit_logs.target_user_id`,
`user_roles.granted_by`, `profiles.status_changed_by`. 감사 기록이 사용자와 함께
사라지면 안 되기 때문이다. **그 기록에 무엇이 담기는지도 확인했다.** 트리거가
넣는 값은 `{"status": "pending"}`과 `{"role": "admin"}`뿐이고 이메일이나 이름은
없다. 그래서 "지웠는데 어딘가 이름이 남는다"가 생기지 않는다.

### 권한 반납이 계정 삭제보다 먼저다

순서를 거꾸로 하면 되돌릴 수 없다. 계정을 먼저 지우면 `google_drive_connections`
행이 cascade로 사라지고, 그 안의 refresh token이 없으면 Google에 반납할 방법이
없다. **우리 기록만 사라지고 사용자의 Google 계정에는 ThreadMark 권한이 그대로
남는다.** 나간 사람의 권한만 남는 것이 가장 나쁜 결말이다.

반납에 실패해도 삭제는 계속한다. Google이 잠시 답하지 않는다고 나가려는 사람을
붙잡아 둘 수는 없다. 화면이 Google 계정 설정에서 직접 끊는 길을 함께 안내한다.

### 실패 문구에 "아무것도 지워지지 않았다"를 쓰지 않는다

권한 반납이 먼저이므로, 계정 삭제가 실패한 시점에는 Drive 연결이 이미 끊겨
있을 수 있다. 자료는 그대로다. 그래서 문구를 "담아둔 자료는 그대로 있습니다.
Google Drive 연결은 끊겼을 수 있으니 설정에서 확인해 주세요"로 적었다.
**실제와 다른 안심은 안심이 아니다.**

### 가드가 있다는 것이 가드가 걸린다는 뜻은 아니다

`guard_last_admin` 트리거가 이미 마지막 관리자 권한 해제를 막고 있다.
그런데 그 트리거는 `postgres`, `service_role`, `supabase_admin`에 예외를 둔다.
복구 작업을 막지 않으려고 일부러 그렇게 두었다. **계정 삭제가 쓰는 클라이언트가
바로 그 service role이다.** 트리거를 믿고 두었다면 하나뿐인 관리자가 앱 안에서
앱을 잠글 수 있었다. 애플리케이션에서 같은 확인을 한 번 더 한다.

관리자 목록은 한 번에 읽어 "이 사람이 관리자인가"와 "관리자가 몇인가"를 함께
판단한다. 따로 물으면 그 사이에 답이 달라질 수 있다.

화면에서도 **미리** 본다(`count_admins()` RPC). 끝까지 적어 넣고 단추를 누른
뒤에 "안 됩니다"를 만나면 사용자는 자기가 무엇을 잘못했는지부터 찾는다.

### 나가는 문을 들어올 수 없는 자리에 달지 않는다

초안은 이 화면의 경로를 `/settings/account`로 적어두었다. 그런데 `(app)`
레이아웃은 `requireActiveAccount`로 승인된 사용자만 통과시킨다. **승인을
기다리는 사람, 거절된 사람, 정지된 사람은 거기에 닿을 수 없다.** 쓰지도 못하고
지우지도 못하는 상태에 갇힌다.

그래서 앱 묶음 밖 `/account/delete`에 두고 로그인만 요구한다. 들어오는 길은
둘이다. `/settings` 맨 아래와 `/pending` 화면 아래. 초안 문서도 함께 고쳤다.

### 확인은 메일 주소를 적게 한다

`삭제` 같은 짧은 낱말은 손이 먼저 움직이고, 한글은 입력기 상태에 따라 엉뚱한
글자가 섞인다. 메일 주소는 화면에 떠 있어 보고 적을 수 있고, 영문이라 입력기와
상관없으며, 무엇보다 **지금 지우려는 계정이 어느 것인지를 눈으로 확인하게
만든다.** 여러 계정을 쓰는 사람에게 이것이 마지막 방패다.

앞뒤 공백과 대소문자는 무시한다. 휴대폰 자판이 첫 글자를 멋대로 크게 바꾸는
일이 흔하고, 그것 때문에 삭제가 막히면 "왜 안 되지"만 남는다.
`tests/account-confirmation.test.mjs`가 통과시킬 것과 막을 것을 양쪽 다 본다.

### 삭제 뒤 로그아웃은 이 기기의 쿠키만 지운다

`signOut({ scope: "local" })`을 쓴다. 계정이 방금 사라져서 서버에 로그아웃을
물어봐도 돌아올 답이 없고, 그 실패로 쿠키가 남으면 사용자는 없는 계정으로
로그인된 채 돌아다니게 된다.

### 만들면서 걸린 것 — 서버 역할이 읽지 못하는 표

처음에는 관리자 수를 세려고 **service role로 `user_roles` 표를 직접 읽었다.**
브라우저에서 눌러보니 "계정을 지우지 못했습니다"가 떴다.

원인은 권한이었다. 이 프로젝트에서는 표를 새로 만들어도 service role에 권한이
자동으로 붙지 않는다. **같은 일을 겪고 남긴 마이그레이션이 이미 있었다.**
(`20260922093000_grant_drive_connections_to_service_role.sql`) 거기 적힌
"새 테이블에 기본 권한이 자동으로 붙는다고 가정했기 때문이다. 이 프로젝트에서는
그렇지 않았다"가 이번 경우와 그대로 겹친다.

**있는 기록을 읽고도 같은 자리에 빠졌다.** 그 기록을 "표를 만들 때의 이야기"로만
읽었고, 지금 쓰려는 것이 그 표라는 것을 잇지 못했다.

고친 방법은 권한을 더하는 것이 아니라 **그 표를 읽지 않는 것**이었다.
관리자 수를 세는 일은 남의 행을 들여다볼 필요가 없고, `count_admins()`가
그 일을 `SECURITY DEFINER`로 대신 해주며 이미 로그인한 사용자에게 열려 있다.
그래서 마이그레이션 없이 끝났다. **권한이 필요해 보이면 권한을 더하기 전에
그 일이 정말 필요한지 먼저 본다.**

판단을 `src/lib/account/last-admin.ts` 한 곳에 두고 화면과 삭제 동작이 같은
함수를 부른다. 각자 세면 어긋날 자리가 생긴다.

## 6. 기능을 추가할 때

새 테이블을 만들면 다음을 함께 한다.

1. 같은 마이그레이션 안에서 RLS를 켜고 정책을 작성한다. 테이블만 먼저 만들지 않는다.
2. `public.is_active_user()`로 승인된 사용자만 접근하게 한다.
3. `npm run db:types`로 타입을 다시 생성한다.
4. `003_rls_isolation_test.sql`에 해당 테이블의 격리 검사를 추가한다.
5. `001_verify_auth_approval.sql`의 테이블 목록과 정책 수를 갱신한다.
6. `SECURITY DEFINER` 함수를 추가했다면 `001`의 허용 목록에 넣고 왜 필요한지 적는다.

검증 스크립트에는 **시간이 지나도 유효한 것만** 넣는다. "아직 사용자가 없다" 같은
초기 상태를 기대하면 운영이 시작된 뒤에는 늘 실패해, 진짜 실패를 가려버린다.

### 검사는 데이터 상태에 기대지 않는다

"자기 승인 상태를 바꿀 수 없다"를 확인할 때 항상 `active`로 바꾸려 시도하면,
이미 `active`인 계정에서는 값이 바뀌지 않아 가드 트리거가 개입하지 않는다.
막히지 않는 것이 정상인데 검사는 실패로 읽는다.

검사는 지금 값을 읽어 **다른 값**으로 바꾸려 시도해야 한다. 누가 어떤 상태든
같은 결론이 나오게 만든다. 데이터가 바뀌면 결과가 달라지는 검사는,
진짜 실패가 생겼을 때 그것을 가려버린다.

### 다른 표를 참조하는 열을 둘 때 주의할 점

외래키 제약은 RLS를 보지 않는다. `captures.source_id`처럼 다른 사용자의 행을 가리킬 수
있는 열은, 참조 대상이 정말 내 것인지 트리거에서 따로 확인해야 한다. 값만 알면
남의 자료에 내 기록을 붙일 수 있기 때문이다. `public.assert_capture_source_owned()`가
그 역할을 한다.

같은 시점에 도는 트리거는 이름 순서대로 실행된다. 소유자를 정하는 트리거와 참조를
확인하는 트리거를 따로 두면, 확인이 먼저 일어나 아직 정해지지 않은 값을 검사하게 된다.
순서에 의존해야 하는 일은 한 함수 안에 순서대로 둔다.

### 조회 정책에 화면 필터를 넣을 때 주의할 점

`sources`의 조회 정책은 접근 통제(`owner_id`, `is_active_user`)와 화면 필터(`deleted_at`)를
함께 담고 있다. 이 조합에는 함정이 있다.

PostgREST는 영향받은 행 수를 세기 위해 갱신을 항상 `RETURNING`으로 감싸고, PostgreSQL은
`RETURNING`이 있는 `UPDATE`에 조회 정책을 갱신된 새 행에도 적용한다. 그래서 **갱신 결과가
조회 정책을 벗어나게 만드는 갱신은 PostgREST를 통해 할 수 없다.** 삭제 표시가 정확히
그런 경우이며, 다음 오류로 실패한다.

```
new row violates row-level security policy for table "sources"
```

`public.soft_delete_source()`가 이 때문에 존재한다. 정책을 느슨하게 하는 대신, 소유자와
승인 상태를 직접 확인하는 `SECURITY DEFINER` 함수로 처리한다. 앞으로 보관 같은 기능을
추가할 때도 같은 제약을 만나게 된다.
