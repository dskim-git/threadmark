# ADR 0002. 승인 상태를 어디서 강제할 것인가

- 상태: 채택
- 날짜: 2026-09-20
- 관련 코드: `src/lib/auth/account.ts`, `src/lib/auth/status.ts`, `src/app/(app)/layout.tsx`
- 관련 문서: ADR 0001, `docs/THREADMARK_PRIVACY_AND_DELETION_DRAFT.md` 1·10절

## 배경

`pending`, `rejected`, `suspended` 사용자는 보호된 앱 데이터에 접근할 수 없어야 한다.
막을 수 있는 자리가 여럿이라 어디를 실제 방어선으로 삼을지 정해야 한다.

후보는 네 곳이다. proxy, 레이아웃, 각 페이지와 Server Action, 그리고 RLS.

## 결정

### 1. 방어선은 RLS이고, 서버 진입점마다 한 번 더 확인한다

데이터 접근을 최종적으로 막는 것은 RLS다. 화면을 거치지 않고 데이터에 닿는 경로가 생겨도
RLS는 함께 우회되지 않는다.

그 위에서 각 페이지, Server Action, Route Handler가 `requireActiveAccount()`를 직접 호출한다.
승인되지 않은 사용자를 이른 시점에 안내 화면으로 보내고, 보호된 화면이 잠깐이라도
렌더링되지 않게 하기 위해서다.

### 2. 레이아웃의 확인만으로 충분하다고 보지 않는다

`src/app/(app)/layout.tsx`도 `requireActiveAccount()`를 호출하지만 이것을 유일한 관문으로
삼지 않는다. Next.js의 레이아웃은 같은 레이아웃을 공유하는 경로 사이를 이동할 때 다시
실행되지 않을 수 있다. 레이아웃 한 번의 확인에 의존하면, 이후 추가되는 하위 경로가
확인 없이 열릴 수 있다.

그래서 이 영역의 각 페이지도 자기 진입점에서 직접 확인한다. 중복처럼 보이지만,
새 페이지를 추가하는 사람이 레이아웃의 동작을 알아야만 안전해지는 구조를 피하려는 것이다.

### 3. proxy는 세션 갱신만 담당한다

`src/proxy.ts`에서 승인 상태를 검사해 리디렉션하지 않는다. 이유는 두 가지다.

첫째, proxy에 접근 통제를 두면 보호 대상 경로 목록을 proxy와 앱 두 곳에서 관리하게 된다.
한쪽만 갱신되는 순간 구멍이 생긴다.

둘째, proxy 단계의 인가 판단은 프레임워크 수준의 우회 가능성이 알려진 영역이다.
세션 쿠키를 갱신하는 일만 맡기면 그런 우회가 인가와 무관해진다.

### 4. 권한 판단에 JWT 클레임의 값을 쓰지 않는다

사용자 ID는 서명을 검증한 클레임에서 얻지만, 승인 상태는 그 ID로 데이터베이스에서 다시 읽는다.

관리자가 어떤 계정을 `suspended`로 바꿔도 이미 발급된 토큰에는 반영되지 않는다.
상태를 토큰에 담아두면 토큰이 만료될 때까지 정지가 실제로 적용되지 않는다.

### 5. 상태를 모르면 거부한다

프로필 조회에 실패하거나, 행이 없거나, 값이 예상 밖이면 접근을 허용하지 않는다.
`canAccessProtectedArea`는 `active` 하나만 통과시킨다.

나중에 상태 값이 추가되더라도 명시적으로 허용하기 전에는 자동으로 열리지 않는다.

### 6. 생성된 데이터베이스 타입과 실행 시점 검증을 함께 쓴다

`npm run db:types`로 원격 스키마에서 `src/lib/supabase/database.types.ts`를 생성하고
Supabase 클라이언트에 적용했다. 타입이 없으면 모든 조회 결과가 `any`가 되어
컬럼 이름 오타조차 드러나지 않는다.

생성된 타입은 컴파일 시점의 약속일 뿐이다. 마이그레이션 후 타입을 다시 생성하지 않으면
코드와 실제 스키마가 어긋난다. 권한을 좌우하는 `status` 값만큼은 `isAccountStatus`로
실행 시점에 한 번 더 확인한다.

**마이그레이션을 추가하고 원격에 적용한 뒤에는 `npm run db:types`를 실행한다.**

### 7. 운영자 문의 주소를 코드에 넣지 않는다

거절·정지 안내 화면의 문의 주소는 `SUPPORT_EMAIL` 환경변수에서 읽는다.
값이 없으면 문의 링크를 표시하지 않는다.

주소는 설정이지 코드가 아니다. 환경마다 다를 수 있고, 관리자 판정에 이메일을 쓰지 않는다는
원칙과 코드를 섞지 않기 위해서다. `NEXT_PUBLIC_` 접두사를 쓰지 않아 브라우저 번들에
포함되지 않는다.

## 결과

- 승인되지 않은 계정은 `/home`에 들어갈 수 없고 `/pending`으로 이동한다.
- 보호된 화면이 잠깐 보였다가 사라지는 일이 없다. 서버에서 먼저 판단한다.
- 로그인 후 기본 이동 경로는 `/home`이다. 승인 여부에 따라 자동으로 갈라진다.

## 남겨둔 것

- 보호된 앱 데이터 테이블의 RLS 정책. `is_active_user()`를 사용해 9~11단계에서 작성한다.
  이 단계까지는 보호할 데이터 자체가 없어 RLS 강제를 실제로 확인할 수 없다.
- 로그인하지 않은 사용자를 위한 랜딩 화면. `/`는 아직 초기 템플릿 상태다.
- 관리자 전용 경로. 6단계에서 `is_admin()`과 같은 방식으로 추가한다.
