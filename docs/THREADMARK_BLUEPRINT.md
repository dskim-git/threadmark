# ThreadMark (TM) Master Blueprint

> 읽고, 남기고, 연결하다.

이 문서는 ThreadMark 개발의 제품 설계서이자 VSCode/AI 코딩 지침이다. 구현을 시작하거나 구조를 변경하기 전에 전체 문서를 읽고, 명시된 핵심 원칙과 범위를 우선한다.

---

## 1. 제품 정의

ThreadMark는 논문, 책, 웹사이트, 음악, YouTube 영상, 영화·드라마·OTT 콘텐츠, PDF, 이미지, 손글씨, 음성 및 일상에서 발견한 생각을 출처와 위치 정보와 함께 저장하고, 프로젝트별로 연결하여 연구·수업·연수에 다시 활용하도록 돕는 개인 지식 작업 공간이다.

서비스명은 **ThreadMark**, 약칭은 **TM**으로 표기한다.

- 공식 GitHub 저장소: https://github.com/dskim-git/threadmark
- 저장소 공개 범위: public
- Vercel Production URL: https://thread-mark.vercel.app/

### 핵심 사용자 가치

1. 자료를 발견한 순간 빠르게 저장한다.
2. 기억할 부분을 페이지, 타임코드, 이미지 영역 등 정확한 위치와 함께 기록한다.
3. 기록을 프로젝트와 연결한다.
4. 키워드 검색과 의미 검색으로 다시 찾는다.
5. 근거와 원출처를 잃지 않은 상태로 논문, 수업 및 연수 자료에 활용한다.

### 핵심 도메인

- **Source**: 논문, 책, 웹사이트, 영상, 이미지 등 기록의 출처가 되는 자료
- **Capture**: Source에서 기억할 인용, 요약, 생각, 질문, 아이디어 또는 독립 메모
- **Project**: 논문, 연구보고서, 수업, 연수 등 Source와 Capture를 활용할 목적

모든 기능은 이 세 개념을 중심으로 설계한다. 자료 유형이 늘어나더라도 핵심 구조를 분리하거나 중복 테이블을 무분별하게 추가하지 않는다.

## 2. 절대 원칙

### 2.1 MathLab 완전 분리

- ThreadMark는 MathLab과 동일한 Supabase 프로젝트를 절대 사용하지 않는다.
- ThreadMark 전용 Supabase 프로젝트를 새로 만든다.
- Supabase URL, publishable key, secret key, 데이터베이스, Auth, Storage bucket을 공유하지 않는다.
- ThreadMark의 migration이나 RLS 변경이 MathLab에 적용될 가능성이 없어야 한다.
- ThreadMark의 Vercel 프로젝트와 환경변수도 MathLab과 분리한다.
- 무료 Supabase 프로젝트 슬롯을 사용할 수 없다면 MathLab 프로젝트를 공유하는 방식으로 우회하지 말고 작업을 중단한 뒤 대안을 결정한다.

### 2.2 저장소 역할 분리

- Supabase Postgres: 사용자, Source, Capture, Project, 태그, 외부 파일 ID 및 검색용 데이터
- Supabase Auth: 회원가입, 로그인 및 사용자 식별
- Google Drive: 사용자 PDF, 이미지, 그림, 음성 등 실제 파일의 기본 저장소
- Supabase Storage: MVP의 기본 파일 저장소로 사용하지 않는다. 향후 명시적 결정이 있을 때만 선택적 fallback으로 추가한다.
- Vercel: Next.js 웹앱과 서버 Route Handler 배포

### 2.3 보안 우선

- 모든 사용자 소유 데이터에는 `owner_id`를 둔다.
- 외부에 노출되는 모든 Supabase 테이블에 RLS를 적용한다.
- 브라우저에서 전달된 `owner_id`를 신뢰하지 않고 인증 세션의 `auth.uid()`를 사용한다.
- `SUPABASE_SECRET_KEY`, Google OAuth client secret, AI API key, TMDB key 등 비밀값을 클라이언트 번들에 포함하지 않는다.
- Google refresh token은 평문으로 저장하지 않는다.
- refresh token은 PostgREST에 노출되지 않는 private schema 또는 서버 전용 저장 영역에 암호화하여 보관한다.
- Google Drive 전체 접근 권한인 `drive` 또는 `drive.readonly`를 기본 요청하지 않는다.
- Google Drive는 최소 권한인 `https://www.googleapis.com/auth/drive.file`과 Google Picker를 우선한다.
- 비공개 Drive 파일을 공개 공유 링크로 바꾸어 표시하지 않는다.

### 2.4 원문과 사용자 생각의 구분

- 직접 인용, 번역, 요약, 바꾸어 쓰기, 사용자의 해석을 데이터와 UI에서 구분한다.
- AI가 생성한 텍스트는 사용자 작성 텍스트와 구분한다.
- AI 요약이나 번역을 연구 근거 자체로 취급하지 않는다.
- 논문 관련 AI 결과에는 가능한 경우 Source, 페이지, 원문 Capture를 함께 표시한다.

### 2.5 기본 공개 범위

- 모든 Source, Capture, Project 및 파일은 기본적으로 `private`이다.
- 메모의 공개 여부와 원본 파일의 공개 여부는 별도로 관리한다.
- 저작권이 있는 PDF는 메모를 공개하더라도 자동 공개하지 않는다.

### 2.6 GitHub 저장소 공개 범위

- ThreadMark GitHub 저장소는 프로젝트 결정에 따라 **public**으로 운영한다.
- 공식 저장소는 `https://github.com/dskim-git/threadmark`이다.
- 저장소가 public인지 private인지와 무관하게 API 및 인증 관련 비밀값을 Git에 저장하지 않는다.
- `.env`, `.env.local`, `.env.*.local`, OAuth client secret, Supabase secret key, AI API key, token 암호화 키를 절대 커밋하지 않는다.
- `.env.example`에는 변수 이름과 설명만 기록하고 실제 값은 넣지 않는다.
- `.gitignore`에 환경변수 파일 차단 규칙을 프로젝트 생성 직후부터 적용한다.
- GitHub secret scanning을 활성화하고 push 전에 비밀값 검사를 수행한다.
- 인증·RLS·Drive OAuth가 완성되기 전에도 공개된 코드는 누구나 검토할 수 있다고 가정하여 최소 권한과 서버 전용 비밀값 원칙을 지킨다.
- 실수로 비밀값을 커밋했다면 파일 삭제만으로 끝내지 않고 해당 키를 즉시 폐기·재발급한다.
- public 저장소라고 해서 자동으로 오픈소스 사용 권한이 부여되는 것은 아니므로, 외부 재사용을 허용할 시점에 `LICENSE`를 별도로 결정한다.

- 구현 후 `lint`, `typecheck`, 테스트, production build를 실행한다.
- 임시 mock을 실제 구현처럼 남기지 않는다.
- 파일 전체를 수정할 때 기존 사용자 변경사항을 보존한다.

### 4.3 Google 로그인 설정 기록

Google 로그인은 Supabase Auth가 처리하고 Google Drive 연결은 앱이 직접 처리한다.
두 흐름은 서로 다른 OAuth client를 사용한다. 한쪽의 client secret이 유출되어도
다른 쪽 연동에 영향이 가지 않게 하기 위해서다. 10.6절에 기록한 client는 Drive 전용이다.

- OAuth client 이름: `ThreadMark Auth`
- 애플리케이션 유형: 웹 애플리케이션
- 승인된 리디렉션 URI: `https://<Supabase 프로젝트 ref>.supabase.co/auth/v1/callback`
- client secret 보관 위치: Supabase 대시보드 Authentication > Providers > Google
- 로그인 단계에서 Drive scope, offline 접근 및 refresh token을 요구하지 않는다.

Supabase Auth URL 설정:

- Site URL: `https://thread-mark.vercel.app`
- Redirect URLs: `http://localhost:3000/**`, `https://thread-mark.vercel.app/**`

앱 콜백 경로는 `/auth/callback`이며 구현 위치는 `src/app/auth/callback/route.ts`다.
로그인 후 돌아갈 경로는 쿠키로 전달한다. 이 값을 `redirectTo`의 쿼리 문자열에 실으면
공급자에게 넘기는 주소가 요청마다 달라져 Supabase의 Redirect URL 허용 목록과 맞추기 어렵고,
맞지 않으면 Supabase가 오류 없이 Site URL로 되돌려 보내 로그인이 조용히 실패한다.
돌아갈 경로는 같은 출처의 경로만 통과시켜 오픈 리디렉션을 차단한다.

개발 중에는 포트가 바뀌면 Redirect URLs에 해당 주소를 추가해야 한다.
개발 환경에서는 등록이 필요한 주소를 서버 로그에 출력한다.

#### 동의 화면에 표시되는 이름 (미해결)

Google은 브랜드 인증을 통과하기 전까지 앱 이름 대신 리디렉션 URI의 도메인을 표시한다.
로그인 콜백이 Supabase 주소이므로 사용자에게는 `<프로젝트 ref>.supabase.co`가 보인다.
브랜드 인증은 승인된 도메인 전부를 Google Search Console에서 소유 증명해야 하는데
`supabase.co`는 증명할 수 없다. Google Cloud에서 앱 이름만 바꿔서는 해결되지 않는다.

`ThreadMark`로 표시하려면 자체 도메인과 Supabase Custom Domain 부가 기능이 필요하다.
월 고정 비용이 발생하므로 실제 사용자를 받기 시작하는 시점에 결정한다.
그때까지는 Google Auth Platform의 Branding에 앱 이름·지원 이메일·홈페이지를 채워둔다.

OAuth 동의 화면 설정은 클라이언트별이 아니라 Google Cloud 프로젝트 전체에 적용된다.
12단계에서 `drive.file` 범위를 추가하면 심사 대상이 되므로, 그 전에 앱을 Production으로
게시하지 않는다.

`place`는 2026-09-25에 더했다. (사용자 요청) 수업 준비의 답사지, 여행 준비의
갈 곳, 책 쓰기의 배경이 되는 곳이 모두 같은 모양이다. **가본 곳과 가볼 곳을
적어두는 자리가 없었다.** 17-1절에 자세히 적었다.

### 5.2 공통 필드

- `id`
- `owner_id`
- `type`
- `title`
- `subtitle`
- `description`
- `thumbnail_url`
- `canonical_url`
- `original_url`

`metadata`는 공급자 응답을 임시로 보관하는 데 사용할 수 있지만, 검색·정렬·관계 설정에 중요한 필드는 정규 컬럼이나 유형별 프로필 테이블에 둔다.

#### 5.2-1 `starred`는 나중에 더한 칸이다 (2026-09-24 정함, 15-A-2)

이 목록에 원래 없던 칸이다. 사용자가 요청해서 더했고, 그 이유를 여기 남긴다.

**왜 필요한가.** 15-A에서 글자로 찾는 길을 만들었다. 그러나 검색은 *무엇을 찾는지
알 때* 쓰는 길이다. "그때 그거 중요했는데"는 낱말이 기억나지 않는다. 읽는 순간에
붙여둔 표시만이 그 물음에 답한다. 22절의 MVP 목록이 검색과 태그를 넣은 것과 같은
이유이며, 별은 그 둘 사이에 있는 가장 싼 길이다.

**왜 boolean 한 칸인가.** 별은 달려 있거나 없거나 둘 뿐이다. 등급(별 다섯 개)은 달
때마다 "이건 넷인가 셋인가"를 생각하게 만들고, 그 생각의 값이 나중에 쓰이지 않는다.
태그(15-B)가 "무엇에 대한 것인가"를 맡고, 별은 "다시 볼 것인가" 하나만 맡는다.
별도 표에 담지 않은 이유는 8.4-2절과 같다. 값 하나에 표 하나는 비싸다.

**별은 `updated_at`을 움직이지 않는다.** 별은 자료의 내용이 아니라 내 주의에 대한
표시다. 제목도 설명도 바뀌지 않는다. 그런데 두 표의 가드 트리거가 모든 갱신에서
`updated_at`을 밀어버리므로, 그대로 두면 `최근에 손댄 순` 정렬이 망가진다. 논문
스무 편에 별을 달면 그 스무 편이 맨 위로 올라오고 실제 수정 순서는 영영 알 수 없다.
그래서 **별만 달라진 갱신에서는 `updated_at`을 그대로 둔다.**

**다는 것과 거르는 것을 함께 만든다.** 달기만 하고 별 단 것만 모아 볼 수 없으면
표시가 아무 일도 하지 않는다. 내 자료 목록(`/library`)에 거르는 길을 함께 두었다.

6.2-1절이 Capture 쪽의 같은 칸이다.

`translation_model`과 `translated_at`은 13-C에서 더했다. 9.4절이 "번역 공급자, 모델,
언어, 생성 시각을 기록한다"고 하는데 이 목록에 모델과 시각을 담을 자리가 없었다.
공급자와 모델을 한 칸에 몰아 적으면 나중에 모델별로 찾아볼 수 없고, 생성 시각을
`updated_at`으로 대신하면 번역문을 고치는 순간 언제 만들어진 번역인지 알 수 없게 된다.

`verification_status`는 `user_written`, `machine_generated`, `user_edited` 셋이다.
9.4절의 "수정본과 AI 원본을 구분할 수 있게 한다"를 맡는 값이고, 기계 번역문을 고치면
데이터베이스 트리거가 `user_edited`로 옮긴다. 화면이 같이 보내주기를 기대하지 않는다.

#### 6.2-1 `starred`는 나중에 더한 칸이다 (2026-09-24 정함, 15-A-2)

5.2-1절과 같은 칸이고 같은 이유로 더했다. 이유는 그쪽에 적었다. 여기는 **왜 Source와
Capture 양쪽에 다 두는가**만 적는다.

**중요한 논문과 중요한 문장은 다른 것이다.** 논문 한 편에 별을 달았다고 그 안의 어느
문장이 중요했는지가 남지 않고, 반대로 문장에만 달면 "이 논문 자체를 다시 봐야 한다"를
적을 자리가 없다. 읽는 일은 두 층에서 일어나므로 표시도 두 층에 있어야 한다.

Capture 쪽 별을 거르는 길은 두 곳에 있다. 빠른 기록(`/inbox`)과 자료를 열었을 때의
기록 목록이다. 자료 없이 남긴 생각과 자료를 읽으며 남긴 생각이 각각 모이는 자리다.

`starred`가 `updated_at`을 움직이지 않는 것도 Source와 같다.

## 7. Project 모델

### 7.1 두 축 (2026-09-24 정함)

ThreadMark는 두 축으로 이루어진다.

| 축 | 무엇 | 어디 |
| --- | --- | --- |
| 모으는 쪽 | 읽은 것과 그때 떠오른 생각 | Source, Capture |
| 만드는 쪽 | 그것으로 내가 만들어 내는 결과물 | Project |

**모으는 쪽이 재료이고 만드는 쪽이 요리다.** 사용자가 정한 비유이며, 이 절의
설계는 전부 여기서 나온다.

따라 나오는 것 넷.

1. **재료는 요리에 들어가도 재료대로 남는다.** 프로젝트에서 자료와 기록의
   원문을 고칠 수 없다. 2.4절의 약속이 여기서도 그대로다. 프로젝트에서
   고치고 싶어지는 것은 *내 글*이지 재료가 아니다.
2. **같은 재료가 여러 요리에 들어간다.** 인용 하나를 2장에서 근거로 쓰고
   4장에서 다시 언급하는 일은 흔하다. 그래서 한 조각이 여러 자리에 놓인다.
3. **손질이 요리의 절반이다.** 재료를 그대로 옮겨 담는 것은 요리가 아니다.
   자리마다 *내가 쓸 글*이 있어야 하고, 재료마다 *이것으로 할 말*이 붙어야 한다.
   이것이 없으면 프로젝트는 태그와 갈라지지 않는다.
4. **재료 쪽에서 어디에 쓰였는지 보인다.** 한 자료가 어느 프로젝트의 어느
   자리에 놓였는지 자료 화면에서 보여준다. 모델에서 거저 나오는 값이다.

### 7.2 프로젝트 공통 정보

- Project는 논문, 연구보고서, 수업, 연수, 웹앱 개발 등 활용 목적을 나타낸다.
- 하나의 Source와 Capture는 여러 Project에 연결할 수 있다.
- 논문 Source의 활용 방식은 프로젝트마다 달라질 수 있으므로 `paper_project_uses`를 별도로 둔다.

필드 예시:

- 프로젝트명
- 프로젝트 유형
- 설명
- 상태
- 시작일·종료일
- 대표 색상
- 공개 범위
- 연구 질문
- 목표 산출물

### 7.3 프로젝트 뼈대 (2026-09-24 더함, 19-A)

프로젝트 아래에 **자리**를 만들고 그 자리를 다시 나눌 수 있게 한다. 논문이면
장과 절, 수업이면 차시와 활동이 되겠지만, **그 이름을 우리가 정하지 않는다.**
사용자가 각 자리에 이름을 적고 필요한 만큼 깊이 나눈다.

`project_outline_nodes`

| 칸 | 뜻 |
| --- | --- |
| `project_id` | 어느 프로젝트의 뼈대인가 |
| `parent_id` | 위 자리. 비어 있으면 맨 위 칸이다 |
| `title` | 자리 이름 |
| `body` | **그 자리에 쓸 내 글** |
| `position` | 형제 사이의 순서 |

**`body`가 이 표의 핵심이다.** 이름만 달 수 있으면 목차일 뿐이다. 자리에
내가 쓸 글이 있어야 모아둔 조각과 내 문장이 같은 자리에 놓인다. 뼈대와 글을
다른 표로 나누지 않는다. 자리 하나에 글 하나이고, 나누면 어느 쪽이 먼저
사라져도 남은 쪽이 떠돈다.

정하는 것들.

- **깊이를 제한하지 않는다.** (2026-09-24, 사용자가 정함) 논문과 수업을 함께
  준비하는데 둘의 깊이가 다르고, 쓰기 전에는 몇 단이 필요한지 알 수 없다.
  우리가 정한 한계에 걸려 못 만드는 편이 더 나쁘다.

  그래서 **깊이를 담지 않는다.** `parent_id`와 `position`만 둔다. 깊이를
  칸으로 담으면 가지를 통째로 옮길 때마다 그 아래 전부를 다시 써야 하는데,
  담지 않으면 부모만 바꾸면 끝난다. 깊이는 화면이 그릴 때 센다.

  깊어질 때 무너지는 것은 데이터가 아니라 **화면**이다. 좁은 화면에서 계속
  들여쓰면 글자가 설 자리가 없어진다. 그래서 **들여쓰기에만 한계를 둔다.**
  일정 단을 넘으면 더 들여쓰지 않고, 자리는 그대로 이어 붙는다. 담는 것에는
  한계가 없고 보여주는 방식만 접는다.

- **단계마다 이름을 정해두지 않는다.** (2026-09-24, 사용자가 정함) 맨 윗단이
  `장`이고 그 아래가 `절`이라고 우리가 정하지 않는다. 논문이면 장과 절이지만
  수업이면 차시와 활동이고, 다른 것일 수도 있다. **자리 이름은 사용자가
  그대로 적는다.** 화면에 단계 이름을 붙이지 않는다.

- **자기 자손 밑으로 옮길 수 없다.** 옮기기를 열어두면 반드시 부딪히는
  고리(cycle)이며, 걸리면 그 가지가 화면에서 통째로 사라진다. 깊이를 담지
  않으므로 트리거가 부모를 따라 위로 거슬러 올라가며 확인한다.
- **번호를 담지 않는다.** `1`, `1.1`, `1.2`는 화면이 순서를 보고 센다.
  담아두면 순서를 바꿀 때마다 어긋난다.
- **날짜 칸을 두지 않는다.** 논문의 장·절에는 날짜가 없다. 수업 차시에는
  있지만, 실제로 수업 준비에 써보고 필요하다고 판단될 때 더한다.
  (`AGENTS.md` 2절 "쓰지 않을 값을 미리 넣지 않는다")
- **자리를 지우면 그 아래도 함께 사라진다.** 다만 **재료는 사라지지 않는다.**
  놓여 있던 자료와 기록은 프로젝트에 그대로 남아 `자리 못 찾은 것`으로 간다.

#### 7.3-1 시작 서식 (2026-09-24 정함, 19-A)

프로젝트를 만들 때 서식을 고르면 **자리 몇 개를 미리 만들어 준다.**
빈 화면을 마주하면 "뭐부터 적지"에서 멈추기 때문이다.

**서식은 시작점이지 울타리가 아니다.** 고른 뒤에는 전부 고치고 지우고 더할 수
있고, **깊이에도 한계가 없다.** 서식이 두 단까지만 주더라도 그 아래로 얼마든지
나눌 수 있다. 형식마다 깊이를 다르게 막지 않는다. 막으면 "논문인데 한 단 더
필요하다"가 생겼을 때 형식을 바꿔야 하고, 그러면 이미 만든 뼈대를 어떻게 할지
또 정해야 한다.

**우리가 지어낸 구성을 넣지 않는다.** 실제로 쓰이는 구성을 찾아 옮겼다.
근거는 `docs/VERIFICATION.md` 4-26절에 적었다.

| 서식 | 무엇을 따랐나 |
| --- | --- |
| 논문 쓰기 | 국내 학위논문의 다섯 장 체제(서론·이론적 배경·연구 방법·연구 결과·논의 및 결론) |
| 수업 준비 | 지도안의 단원 개관과 본시 흐름(도입·전개·정리), 평가 계획 |
| 연수 준비 | 교원 직무연수 계획의 연수 목표·내용·운영·평가 |
| 책 쓰기 | 출간기획서가 묻는 것(기획 의도·예상 독자·차례)과 원고 자리 |
| 발표 준비 | 남길 말 한 줄을 맨 앞에 두는 구성 |
| 웹앱·프로그램 만들기 | 제품 요구사항 문서(PRD)의 기획 항목에 설계·보안·배포를 이어 붙인 것 |
| 여행 준비 | 예산을 먼저 정하고 예약·일정·짐으로 이어가는 순서 |
| 자유 형식 | 자리를 만들지 않는다 |

정하는 것들.

- **서식 이름은 이미 있는 `projects.project_type` 칸에 들어간다.** 서식을
  담을 칸을 따로 만들지 않는다. 같은 뜻의 칸이 두 벌이 되면 어긋난다.
  고른 뒤에 사용자가 고쳐 적을 수 있다.
- **서식은 만들 때 한 번만 적용된다.** 프로젝트와 서식을 묶어두지 않는다.
  묶으면 "서식을 바꾸면 이미 쓴 글은 어떻게 되나"라는 물음이 생기는데,
  그 물음에 좋은 답이 없다.
- **자리 이름에 번호를 담지 않는다.** `Ⅰ. 서론`이 아니라 `서론`이다.
  번호는 화면이 센다. (7.3절)
- **이미 만든 프로젝트에 서식을 얹는 길은 두지 않는다.** 필요해지면 그때
  만든다. 지금 만들면 "이미 있는 자리와 어떻게 섞을 것인가"를 추측으로
  정하게 된다.

### 7.4 자리에 놓는 재료 (19-B)

`project_node_items`

| 칸 | 뜻 |
| --- | --- |
| `node_id` | 어느 자리에 놓는가 |
| `source_id` 또는 `capture_id` | 무엇을 놓는가. 둘 중 정확히 하나 |
| `note` | **이 재료로 여기서 할 말** |
| `position` | 자리 안에서의 순서 |

`source_projects`·`capture_projects`는 그대로 둔다. 그 둘은 **"이 프로젝트에
쓸 것으로 모아둔 것"**이고, 이 표는 **"그중 어디에 놓았는가"**다. 합치면
모으기와 배치라는 두 동작이 하나로 뭉개진다.

그 차이가 화면에서 `자리 못 찾은 것` 칸이 된다. 프로젝트에 이어두었지만 아직
어느 자리에도 놓이지 않은 것들이며, 실제 작업에서 가장 자주 보게 될 자리다.

정하는 것들.

- **같은 것을 여러 자리에 놓을 수 있다.** (7.1절 2번) 대신 **같은 자리에
  같은 것을 두 번 놓을 수는 없다.** 짝에 `unique`를 건다.
- **놓으면 프로젝트에도 자동으로 잇는다.** 자리에 놓았는데 프로젝트 목록에
  없는 상태가 생기면, 어느 쪽이 맞는지 알 수 없게 된다.
- **남의 재료를 놓을 수 없다.** 외래키 제약은 RLS를 보지 않는다. 자료 id만
  알면 남의 것을 붙일 수 있으므로 트리거가 소유자를 확인한다.
  (`assert_source_owned`, `assert_capture_owned`)

### 7.5 조망 (19-C)

프로젝트를 열면 구조가 먼저 보인다. 들여쓴 트리에 자리마다 놓인 개수가 함께
보이고, 그것이 곧 "지금 어디까지 했나"에 답한다.

자료 화면에서는 거꾸로 본다. 이 자료가 어느 프로젝트의 어느 자리에 놓여
있는지 보여준다. (7.1절 4번)

### 7.6 나중에 정할 것

- **`paper_project_uses.planned_section`과의 관계.** 8.3절의 그 칸은 지금
  자유 글이고 "원고의 어디에 넣을 것인가"를 적는다. 뼈대가 생기면 그 칸이
  뼈대 자리를 가리키게 만들고 싶어지는데, **같은 뜻의 칸이 두 벌이 되면
  반드시 어긋난다.** 뼈대를 실제로 써본 뒤에 어느 쪽을 없앨지 정한다.
- ~~**뼈대 서식(템플릿).**~~ **만들었다.** 7.3-1절 `시작 서식`이다.
  "몇 번 만들어 보고 무엇이 반복되는지 안 뒤에 만든다"고 적어두었는데,
  그러지 않고 **밖에서 실제로 쓰이는 구성을 찾아다 옮겼다.** 우리가 몇 번
  만들어 보는 것보다 이미 쓰이는 것을 보는 편이 근거가 확실하다.
  근거는 `docs/VERIFICATION.md` 4-26절에 표로 적었다.
- **메뉴를 두 축으로 나누기.** 지금 메뉴는 평평해서 모으는 일과 만드는 일이
  같은 무게로 보인다. 다만 메뉴를 바꾸는 것은 쓰던 사람이 길을 잃는 변화라,
  뼈대를 써본 뒤에 이야기한다.
- ~~**읽다가 바로 자리에 보내기.**~~ **만들었다.** (19-B 뒤, 사용자 요청)
  기록 카드와 자료 화면에 `자리에 놓기`가 붙었고, 왼쪽에서 프로젝트를
  오른쪽에서 자리를 고른다. **적어둔 직후가 그 판단이 가장 또렷한 때다.**
  기록만 되다가 자료도 되게 넓혔다. 자료를 통째로 `3장에 쓸 논문`으로
  정해두는 일이 오히려 더 흔했다.

#### 8.3-1 `status`의 값과 계획이 붙는 자리 (2026-09-23 정함, 14-D-1)

이 절에 `status` 칸만 있고 값이 없었다. 구현하면서 둘로 정했다.

| 값 | 뜻 |
| --- | --- |
| `planned` | 아직 쓸 예정 |
| `used` | 원고에 넣었음 |

논문이 여러 편 쌓이면 "어느 것을 이미 처리했더라"가 곧 물음이 된다. 그 물음에
답하는 것이 이 칸의 유일한 일이므로, 값이 하나면 칸 자체가 아무 일도 하지
않는다. `AGENTS.md` 2절의 "값 하나만"에서 벗어난 유일한 열거형이며, 그 이유를
같은 곳에 적어두었다.

계획은 **논문과 프로젝트의 짝마다 하나**다. 짝에 `unique`를 걸고, 만든 뒤에는
양쪽을 바꿀 수 없게 했다. 바꿀 수 있으면 A 논문을 두고 적은 계획이 B 논문의
것이 된다.

`source_projects`의 연결이 있어야 계획이 의미가 있으므로 화면은 연결된
프로젝트에만 계획 칸을 보여준다. 그러나 **데이터베이스로 강제하지 않는다.**
연결을 가리키는 외래키를 걸면 연결을 끊는 순간 적어둔 계획이 함께 사라진다.
연결을 끊어도 계획은 남고, 화면은 "연결은 끊겼고 계획은 남아 있다"를 알린다.

8.2절의 분석 서식과 겹치지 않는다. 분석 서식은 논문 한 편에 하나로
"이 논문이 무엇을 말하는가"를 적고, 여기는 "내 원고의 어디에 넣을 것인가"를
프로젝트마다 적는다.

- 후속 읽기

#### 8.4-1 방향과 제약 (2026-09-23 정함, 14-D-2a)

이 절에 관계 여덟 가지만 있고 표의 모양이 없었다. 구현하면서 정했다.

**관계에는 방향이 있다.** 출발 자료와 도착 자료를 나눠 담는다. A가 B를 인용하는
것과 B가 A를 인용하는 것은 다른 사실이다. 목록에 `인용함`과 `인용됨`이 나란히
있는 것도 이 때문이다. 어느 쪽에서 적기 시작했는지에 따라 고르는 말이 다르다.
화면은 어느 쪽에서 보든 화살표로 방향을 그대로 보여준다.

**논문 전용이 아니다.** 13.1절이 같은 표로 음악의 여러 버전을 잇는다. 그래서 열
이름을 `paper_`로 시작하지 않고 자료 일반으로 두었고, 화면도 논문 유형으로
제한하지 않는다. 여기 여덟 가지는 논문용이며 음악용 관계는 15단계에서 더한다.

**고치지 않는다.** 잇거나 끊는 것뿐이라 `UPDATE` 권한을 주지 않는다. 관계를 잘못
골랐다면 끊고 다시 잇는다. `source_projects`와 같다.

**막는 것 둘.** 자기 자신과는 잇지 못한다. 같은 짝에 같은 관계는 하나만 둔다.
똑같은 줄이 둘이면 화면에서 어느 것을 끊어야 할지 알 수 없다.

관계에 "왜 이렇게 이었는지"를 적는 칸은 두지 않았다. 이 절에 없는 칸이라 추측해서
만들지 않았다. 실제로 이어보고 필요하면 그때 더한다.

#### 8.4-2 읽을 후보는 표가 아니라 자료의 상태다 (2026-09-23 정함, 14-D-2b)

후보를 담는 표를 따로 두지 않았다. `sources.status`에 `reading_candidate` 값을
더했다. 5.2절의 그 칸이다.

별도 표에 담으면 제목·관계·서지 정보를 담는 길이 두 벌이 되고, 정식 자료로 바꿀
때 옮겨 담아야 한다. 옮기는 코드는 반드시 무언가를 빠뜨린다. 상태로 두면
**전환이 곧 상태 바꾸기**이고 옮길 것이 없다. 담아두는 순간부터 8.4절의 관계로
이어지고, 8.1절의 서지 정보와 8.2절의 분석 서식도 그대로 쓴다.

전환은 **한 방향뿐이다.** 읽을 후보에서 정식 자료로만 간다. 되돌릴 수 있게 두면
인용과 메모와 파일이 붙은 논문이 "아직 안 읽은 것"이 되고, 그 상태에서 무엇이
진짜인지 알 방법이 없다. 잘못 담아두었다면 지운다.

담아두기와 잇기를 한 번에 한다. 관계 없이 담아두면 어디서 봤는지가 남지 않는데,
그 출처가 바로 지금 읽고 있는 자료다. 기본 관계는 `참고문헌에서 발견`이다.

DOI는 적어둘 수 있다. 8.1절의 `paper_profiles`에 DOI만 담고, 전환한 뒤 8.5절의
`DOI로 가져오기`가 그 값으로 나머지를 채운다. 전환할 때 자동으로 가져오지는
않는다. 사용자가 손으로 고쳐둔 값을 말없이 덮어쓰게 되기 때문이다.

- KCI
- RISS

MVP는 사이트 검색 바로가기를 제공한다. Google Scholar 비공식 스크래핑에 의존하지 않는다. KCI와 RISS API도 공식 이용 조건이 확인되기 전에는 핵심 기능의 의존성으로 삼지 않는다.

- RIS 가져오기
- PDF 업로드 또는 Drive 선택
- 수동 입력

### 8.5-1 서지 정보를 어디서 가져올 수 있는가 (2026-09-23 확인)

14-C를 만들면서 실제로 물어보고 알아낸 것이다. 추측이 아니라 응답을 확인했다.

| 곳 | 한글 제목으로 찾기 | 키 | 비고 |
| --- | --- | --- | --- |
| Crossref | **불가** | 불필요 | DOI로는 국내 논문도 잘 나온다 |
| OpenAlex | **불가** | 불필요 | Crossref에서 받아오므로 같은 한계 |
| KCI OpenAPI | 가능 | **필요** | `open.kci.go.kr`에서 신청 |
| RISS | — | — | 공개 API 없음 |

**Crossref는 한글 제목을 색인하지 않는 것이 아니라 가지고 있지 않다.**
국내 학술지가 DOI를 등록할 때 영문 제목과 로마자 저자명만 올리기 때문이다.
국내 학술지 논문 여덟 편을 열어 확인했다.

```text
title          : Supporting Students' Argumentation Structure Construction…
original-title : (없음)
author         : {"given": "Kyeong-Hwa", "family": "Lee"}
```

`query`, `query.title`, `query.bibliographic` 어느 쪽으로 물어도 한글 검색어에는
`total: 0`이 돌아온다. 그래서 화면은 한글이 섞인 검색어를 아예 보내지 않고
미리 알려준다. 보내봐야 빈손으로 돌아오고 그동안 사용자는 기다린다.

OpenAlex도 한글 검색어로 결과를 주기는 하지만 관련 없는 논문이 온다.
"결과가 있다"와 "맞는 결과가 있다"는 다르다.

KCI OpenAPI는 살아 있고 한글 제목을 파라미터로 받는다. 키 없이 부르면
`필수 요청 파라미터가 없음 => key`가 돌아온다. 붙이게 되면 **보조 수단**으로
둔다. 키가 없어도 나머지 길(PDF에서 DOI 찾기, DOI 직접 입력, AI 보조)이
그대로 돌아가야 한다. 위의 "핵심 기능의 의존성으로 삼지 않는다"가 그 뜻이다.

### 8.5-2 국내 논문의 서지 정보를 채우는 길

셋이고, 듣는 경우가 서로 다르다.

| 길 | 듣는 경우 | 나오는 저자 이름 |
| --- | --- | --- |
| PDF에서 DOI 찾기 → Crossref | PDF에 DOI가 인쇄되어 있을 때 | 로마자 |
| AI가 PDF 첫 장 읽기 | PDF는 있는데 DOI가 없을 때 | **한글 그대로** |
| KCI 검색 | PDF가 없거나 논문을 찾는 단계 | 한글 |

국내 학위논문과 오래된 논문에는 DOI가 없는 일이 잦아 두 번째가 필요하다.
Crossref로 가져오면 저자가 `Lee, Kyeong-Hwa`로 오는데, 한글 이름을 쓰려면
손으로 고쳐야 한다. AI가 첫 장을 읽으면 인쇄된 그대로 `이경화`가 나온다.

### 8.5-3 검색 바로가기에서 주소로 검색어를 넘길 수 있는 곳 (2026-09-23 확인)

| 사이트 | 방식 |
| --- | --- |
| DBpia, Google Scholar, ERIC, OpenAlex | 주소에 검색어를 실어 바로 검색 |
| KCI, RISS, Crossref, ScienceON | **검색어를 복사해 두고 검색 화면만 연다** |

뒤쪽 넷은 주소로 검색어를 받지 않는다. 되는 척하지 않고 붙여넣게 한다.
검색어를 실어 보내놓고 빈 화면이 뜨면 사용자는 우리 기능이 고장 난 줄 안다.

**이 목록은 브라우저에서 사람이 눌러보고 정한 것이다.** 서버에서 받아본
응답으로는 판단할 수 없다. 응답이 200이어도 검색어를 무시했을 수 있고,
검색어가 응답에 여러 번 나와도(RISS가 그랬다) 장식에 섞인 것일 수 있다.
요즘 사이트는 화면을 자바스크립트로 그려서 서버는 껍데기만 준다.
고치거나 더할 때도 브라우저에서 확인한다.

Crossref 웹사이트는 목록에 두되 없어도 된다. 앱이 이미 Crossref API로
직접 묻는다. DOI 입력과 영문 제목 검색이 그것이다.

## 9. PDF 뷰어, 위치 기억 및 번역

### 9.1 PDF 표시

- PDF.js를 사용한다.
- 데스크톱에서는 좌측 PDF, 우측 Capture 패널의 분할 화면을 사용한다.
- 모바일에서는 `PDF`와 `메모` 탭을 전환한다.
- 마지막 열람 페이지와 확대율을 사용자별로 기억한다.
- 파일은 Google Drive에서 읽어 브라우저 메모리의 PDF.js로 전달한다.
- Google Drive preview iframe만으로 구현하지 않는다. 교차 출처 iframe 내부의 선택 텍스트와 좌표에 앱이 접근할 수 없기 때문이다.

#### 9.1-1 분할 화면은 13-A에서 지키지 않았고 14-E에서 고쳤다 (2026-09-23)

13-A는 위의 "좌측 PDF, 우측 Capture 패널"을 그대로 만들지 않았다. PDF를 넓게
펴놓고 고른 문장을 떠 있는 창으로 받는 방식이다. 14-B의 분석 서식도 별도
화면이라, 논문을 옆에 두고 채울 수 없다.

13-C에서 그 창이 화면 밖으로 넘치고 눌러도 닫히던 문제가 있었는데, 따지고
보면 분할 화면에 있어야 할 것을 떠 있는 창으로 만든 데서 온 것이다.
창이 작을 때는 드러나지 않다가 번역 칸이 붙으면서 드러났다.

14-E에서 9.1절대로 고쳤다. 오른쪽 패널에 셋이 온다.

- 분석 서식 (8.2절)
- 이 자료의 기록 목록
- 고른 문장 · 페이지 메모

셋을 탭으로 묶었다. 9.1절이 "Capture 패널"이라고만 한 것은 분석 서식이
생기기 전이라서다. 모바일에서는 9.1절과 21절대로 `PDF`/`메모` 탭을 전환한다.

떠 있던 창을 걷어내자 그 창 때문에 필요했던 코드도 함께 사라졌다. 화면
크기를 재서 자리를 잡고, 위아래 공간을 견주고, 창 안의 누름을 가려내던
것이 모두 없어졌다. **분할 화면이었다면 처음부터 없어도 될 코드였다.**

좌우 너비는 가운데를 끌어 바꾼다. 우리가 정하지 않는 이유는 알맞은 너비가
화면 크기와 논문 편집 형태에 따라 다르기 때문이다. 2단 편집 논문은 넓어야
읽히고 한글 학위논문은 좁아도 된다. 정한 너비는 브라우저에 기억해 둔다.

### 9.2 Google Drive PDF 전달

- 브라우저에 장기 refresh token을 전달하지 않는다.
- 서버가 사용자 세션을 확인한 후 Drive 파일을 스트리밍한다.
- 가능하면 HTTP Range 요청을 전달하여 큰 PDF를 효율적으로 읽는다.
- 앱 서버나 브라우저의 임시 데이터는 영구 저장소로 취급하지 않는다.
- Drive 파일 ID, MIME type, size, checksum, modified time을 DB에 저장한다.
- 파일이 교체된 경우 checksum을 비교하여 기존 annotation 위치가 달라질 수 있음을 표시한다.

### 9.3 텍스트 PDF 동작 기대치

공식 논문 사이트에서 내려받은 born-digital PDF는 일반적으로 다음 기능이 잘 작동할 가능성이 높다.

- 페이지 인식
- 텍스트 드래그 선택
- 선택 문장 복사
- 페이지 번호 기록
- 선택 영역 좌표 기록
- 해당 페이지 재이동
- 선택 문장 번역

그러나 다음 경우에는 오차가 생길 수 있다.

- 스캔 이미지 PDF
- 복사 방지가 적용된 PDF
- 글꼴 인코딩이 비표준인 PDF
- 2단 편집에서 여러 단을 가로질러 선택한 경우
- 수식, 표, 각주, 합자 및 하이픈 처리
- OCR 결과의 문단 순서가 잘못된 경우

따라서 위치 앵커는 `페이지 + 선택 문장 + 주변 문맥 + 좌표 + 파일 checksum`을 함께 저장한다. 좌표만 저장하지 않는다.

### 9.4 부분 번역

사용자가 PDF 텍스트를 선택하면 작은 컨텍스트 메뉴를 표시한다.

```text
[Capture로 저장] [번역] [인용 저장] [내 생각 추가]
```

번역 흐름:

1. 선택한 텍스트와 페이지 정보를 가져온다.
2. 선택된 부분만 서버 번역 API로 전송한다.
3. 원문과 번역문을 나란히 표시한다.
4. 사용자가 `번역과 함께 저장`을 선택하면 Capture로 저장한다.
5. 번역 공급자, 모델, 언어, 생성 시각을 기록한다.

원칙:

- 논문 전체를 자동 전송하지 않는다.
- 기본 대상 언어는 사용자 설정에서 정한다.
- 원문은 수정하지 않는다.
- 기계 번역임을 표시한다.
- 번역 결과는 사용자가 수정할 수 있다.
- 수정본과 AI 원본을 구분할 수 있게 한다.
- 번역 API는 교체할 수 있도록 provider interface로 추상화한다.

초기에는 향후 사용할 생성형 AI API를 짧은 선택 번역에도 재사용할 수 있다. 이후 필요하면 DeepL 또는 Google Cloud Translation을 별도 provider로 추가한다.

### 9.5 OCR

스캔 PDF에 대한 OCR은 MVP 범위에서 제외한다. 텍스트 레이어가 없는 파일을 감지하면 다음 안내를 표시한다.

```text
이 PDF에서는 선택 가능한 텍스트를 찾지 못했습니다.
페이지 메모는 사용할 수 있으며 OCR 기능은 추후 지원됩니다.
```

## 10. Google Drive 중심 파일 저장

### 10.1 연결 흐름

1. 사용자가 ThreadMark에 로그인한다.
2. 설정에서 `Google Drive 연결`을 선택한다.
3. 별도의 OAuth 동의 과정을 진행한다.
4. 최소 권한 `drive.file`을 요청한다.
5. 앱이 사용자의 My Drive에 `ThreadMark` 루트 폴더를 생성한다.
6. 루트 폴더 ID를 사용자 설정에 저장한다.
7. 필요한 하위 폴더를 앱이 생성한다.

권장 폴더:

```text
ThreadMark/
  Papers/
  PDFs/
  Images/
  Drawings/
  Audio/
```

물리적 폴더 구조를 Source·Project 관계와 동일하게 만들지 않는다. 한 Source가 여러 Project에 속할 수 있기 때문이다. Drive는 파일 저장, ThreadMark DB는 의미상 분류를 담당한다.

### 10.2 기존 Drive 파일

- Google Picker로 사용자가 직접 파일을 선택한다.
- 앱은 사용자가 선택하거나 앱이 생성한 파일만 접근한다.
- 광범위한 전체 Drive 읽기 권한을 기본 요청하지 않는다.

### 10.3 업로드

- 브라우저에서 선택한 파일을 Google Drive API로 업로드한다.
- 큰 파일은 resumable upload를 사용한다.
- 업로드 성공 후에만 Source와 attachment 상태를 `ready`로 변경한다.
- 업로드 도중 실패한 DB 레코드와 orphan 파일을 정리하는 작업을 둔다.

### 10.4 연결 해제 및 오류

- 사용자가 Drive 권한을 취소할 수 있다.
- 토큰 만료, 권한 취소, 파일 이동·삭제를 구분해 표시한다.
- Drive 파일이 사라져도 Source와 Capture 메타데이터는 유지한다.
- `다시 연결`, `새 파일 연결`, `메타데이터만 유지` 선택지를 제공한다.
- Drive가 연결되지 않아도 URL Source와 텍스트 메모는 사용할 수 있다.

### 10.5 토큰 저장

- access token은 단기 사용한다.
- refresh token은 서버 전용으로 암호화 저장한다.
- 클라이언트가 refresh token 테이블을 select할 수 없어야 한다.
- 암호화 키는 Vercel 환경변수에 저장한다.
- 로그에 token, authorization header, signed URL을 남기지 않는다.

### 10.6 개발·배포용 Google 설정 기록

- OAuth client 이름: `ThreadMark Local Web`
- 애플리케이션 유형: 웹 애플리케이션
- 승인된 JavaScript 원본: `http://localhost:3000`, `http://localhost:3001`, `https://thread-mark.vercel.app`
- 승인된 리디렉션 URI: `http://localhost:3000/api/google-drive/callback`, `http://localhost:3001/api/google-drive/callback`, `https://thread-mark.vercel.app/api/google-drive/callback`
- callback 구현 위치: `src/app/api/google-drive/callback/route.ts`
- Picker API key 이름: `ThreadMark Picker Local`
- 웹사이트 제한: `http://localhost:3000/*`, `http://localhost:3001`, `http://localhost:3001/*`, `https://thread-mark.vercel.app/*`, `https://docs.google.com/*`
- API 제한: Google Picker API, Google Drive API

> **개발 서버는 3001번에서 뜬다.** 3000번은 다른 앱이 쓰고 있다.
> 처음에는 3000번만 등록해 두었는데, Google은 주소를 글자 단위로 비교하며
> 와일드카드를 받지 않는다. 그래서 포트가 다르면 완전히 다른 곳으로 본다.
>
> 이 때문에 두 번 막혔다. 12-A에서는 OAuth 리디렉션이, 12-C에서는 Picker의
> API key가 걸렸다. Picker는 `The API developer key is invalid.`라는 문구를
> 보여주는데, 키 값이 틀렸다는 뜻이 아니라 **그 주소에서는 못 쓴다**는 뜻이다.
> 2026-09-22에 3001번을 모두 추가해 해결했다.
- OAuth scope: `https://www.googleapis.com/auth/drive.file`
- Google Picker App ID로 사용할 Google Cloud 숫자형 프로젝트 번호를 비공개로 확인·기록했다.
- OAuth client secret, API key, 프로젝트 번호 등 환경별 값은 저장소에 커밋하지 않는다.

공식 참고:

- Drive 최소 권한 및 Picker: https://developers.google.com/workspace/drive/api/guides/api-specific-auth
- 폴더 생성: https://developers.google.com/workspace/drive/api/guides/folder
- 파일 업로드: https://developers.google.com/workspace/drive/api/guides/manage-uploads

### 13.4 음악 Capture

지원할 메모 유형:

- 곡 전체에 대한 감상
- 특정 재생 시점 또는 구간 메모
- 기억하고 싶은 짧은 가사 구절
- 가사 해석 또는 번역
- 멜로디·리듬·악기·편곡에 대한 메모
- 특정 장면·사람·여행·시기와 연결된 기억
- 수업·연수·영상 배경음악 활용 아이디어
- 비슷한 곡 또는 관련 작품
- 다시 듣고 싶은 이유
- 분위기, 감정, 상황 태그

예:

```text
01:08–01:34 / 2절 후렴
현악기가 들어오면서 분위기가 확장되는 부분.
연구 발표 영상의 도입부 분위기와 잘 어울릴 것 같다.
```

Capture를 선택하면 지원되는 플레이어에서 해당 시점으로 이동한다. 공급자가 시점 이동을 지원하지 않으면 시간을 표시하고 외부 재생 링크를 제공한다.

- 집중할 때
- 수업 준비
- 여행
- 휴식
- 자신감
- 그리움
- 발표·영상 배경음악 후보

이 값들은 일반 Tag로 저장하며 고정 목록으로 제한하지 않는다.

#### 13.3-1 한국 음악을 어디서 찾을 수 있는가 (2026-09-24 확인, 15-E)

13.3절이 "MusicBrainz를 기본 공개 메타데이터 공급자로 우선 검토한다"고 하고,
"메타데이터가 없거나 한국 음악 정보가 불완전할 수 있으므로"라고 미리 걱정해
두었다. 실제로 받아보고 확인했다.

**결론부터. MusicBrainz는 한국 음악을 안다. 다만 칸을 나눠 물어야 한다.**

처음에 `아이유 밤편지`처럼 뭉뚱그려 물었더니 엉뚱한 것이 왔다. `붉은 노을
이문세`에 MC 스나이퍼의 판이 오고 `BTS Dynamite`에 남이 부른 커버가 왔다.
`recording:"밤편지"`처럼 칸을 나눠 묻자 달라졌다.

| 곡 | MusicBrainz | iTunes |
| --- | --- | --- |
| 밤편지 / 아이유 | **밤편지 / IU** | Through the Night / IU |
| 주저하는 연인들을 위해 / 잔나비 | **주저하는 연인들을 위해 / 잔나비** | For Lovers Who Hesitate / JANNABI |
| 붉은 노을 / 이문세 | **붉은 노을 / 이문세** | Sunset Glow / BIGBANG |
| Antifreeze / 검정치마 | **Antifreeze / 검정치마** | Antifreeze / The Black Skirts |
| 가시나무 / 시인과 촌장 | **가시나무 / 시인과 촌장** | 가시나무 / Towner & Town Chief |

**MusicBrainz는 한글 제목과 한글 아티스트를 그대로 준다.** 1988년 음반까지
있다. 정확도 점수(0~100)도 함께 주므로 후보를 늘어놓을 때 쓸 수 있다.
표지는 Cover Art Archive에서 판 id로 받는다. 있는지는 확인했다.

**iTunes는 찾기는 잘 하지만 이름을 바꿔 준다.** `밤편지`가 `Through the
Night`으로, `검정치마`가 `The Black Skirts`로 온다. `시인과 촌장`은
`Towner & Town Chief`로 기계번역해 놓았다. 대신 **표지·장르·정확한 발매일**은
이쪽이 좋다. MusicBrainz는 그 셋이 약하다.

**그래서 둘을 함께 쓰고 사람이 고른다.** 13.3절의 "후보 목록에서 정확한 버전
선택"이 그것이다. 우리가 하나를 골라주면 `붉은 노을`에 BIGBANG의 판이 들어간다.
후보마다 어디서 왔는지 밝힌다. 밝히지 않으면 "왜 영문으로 나오지"를 묻게 된다.

MusicBrainz를 앞에 두고 iTunes를 뒤에 둔다. 13.3절이 MusicBrainz를 기본으로
두고 Apple Music을 "선택적 공급자"로 취급하라고 한 것과 맞고, 한쪽이 죽어도
나머지로 굴러간다. 같은 절의 "특정 상용 서비스 하나에 종속되지 않게 한다"다.

**빠뜨리기 쉬운 것 둘.**

`country=KR`을 붙이면 iTunes가 **무엇을 물어도 0건**을 돌려준다. 확인하고
알았다. 붙이지 않으면 기본 창구로 가고 그쪽에도 한국 음악이 있다.

아티스트를 함께 넣으면 오히려 못 찾는 경우가 있다. `밤편지`에 `아이유`를
넣으면 0건이다. MusicBrainz에 `IU`로 올라가 있기 때문이다. 그래서 아티스트로
못 찾으면 **곡 이름만으로 다시 묻고**, 그렇게 찾았다고 알린다.

**아직 못 하는 것.** 작곡·작사·편곡은 대체로 오지 않는다. 아주 최근에 나온
곡이나 국내 인디 음악은 등록되지 않은 것이 있다. 그래서 손으로 적는 길을
그대로 둔다. 찾아오기는 손을 덜어주는 일이지 조건이 아니다.

#### 13.5-1 수동 등록에서 정한 것 (2026-09-24 정함, 15-D)

22절 MVP 목록의 "음악 Source 수동 등록, 공급자 링크 및 시간 위치 Capture"를
구현하면서 정한 것을 적는다. 13.3절의 자동 메타데이터는 MVP 이후다.

**재생 시점을 초로 담는다.** 13.4절의 `01:08–01:34`를 글로 담으면 `1:08`과
`01:08`이 다른 값이 되어 정렬도 비교도 안 된다. 담는 것은 숫자이고 사람이
보는 모양은 `src/lib/music/time.ts`가 만든다. 20-1절에서 태그의 이름과
판정값을 나눈 것과 같은 생각이다.

`1:08`, `01:08`, `68` 셋을 같은 뜻으로 읽는다. 그러나 `1:75`는 **받지 않는다.**
`2:15`를 뜻할 수도 있고 잘못 친 것일 수도 있는데, 우리가 고쳐 담으면 사용자가
친 것과 담긴 것이 달라진다. 초만 적은 `75`는 모양이 달라 뜻이 분명하므로 받는다.

**끝 시점은 없을 수 있다.** "여기부터 저기까지"가 아니라 "이 순간"을 가리키는
메모가 있다. 없는 값을 시작과 같게 채우면 그 둘을 구분할 수 없다.
9절의 쪽 메모에서 문맥과 좌표를 비워둔 것과 같다.

**공급자 링크에 서비스 이름을 담지 않는다.** 주소에서 알아본다. 담게 하면
`spotify`와 `Spotify`가 섞이는 것보다 더 나쁜 일이 생긴다. **고른 것과
붙여넣은 주소가 어긋나는 것을 아무도 막지 못한다.** 스포티파이를 고르고
유튜브 주소를 넣어도 통과한다. 주소가 곧 답이라 물을 필요가 없다.

13.2절이 Spotify·Apple Music·YouTube Music을 들지만, 13.3절이 "특정 상용
서비스 하나에 종속되지 않게" 하라고 하므로 국내 서비스(멜론·벅스·지니뮤직·
바이브·FLO)도 함께 알아본다. **모르는 곳이면 주소의 이름을 그대로 보여주고
담게 한다.** 목록에 없다고 막지 않는다. 국내 서비스는 이 목록보다 자주 바뀐다.

**발매일을 글로 담는다.** `2024-03-15`도 `2024년 3월`도 `2024`만도 온다.
옛 음반은 달까지만 알려진 것이 흔한데, 날짜로 담으려면 모르는 자리를
지어내야 한다. 8.1절의 권·호·쪽, 11.1절의 게시일과 같은 판단이다.

**ISRC와 MusicBrainz ID를 두지 않았다.** 13.2절에 있지만 손으로 적는 값이
아니다. 기계가 채우는 식별자이고 그것을 채우는 기능이 MVP 이후다. 지금 칸만
만들어두면 빈 칸이 화면에 남아 "여기는 왜 안 되지"를 묻게 된다. 자동
가져오기를 만들 때 20절의 `source_external_ids`와 함께 정한다.

**시점을 눌러 이동하지 않는다.** 13.4절이 "지원되는 플레이어에서 해당 시점으로
이동한다"고 하지만, 그 플레이어를 붙이는 일은 MVP 이후다. 지금은 시간을 적어
보여주고 외부 링크를 함께 둔다. 13.4절 마지막 문장이 허용하는 쪽이다.
누를 수 있게 해두면 눌러야만 아무 일도 없다는 것을 알게 된다.

## 17-1. 장소 기능 (2026-09-25 더함, 사용자 요청)

### 17-1.1 왜 필요한가

> 장소 기록이 수업 준비나 책쓰기, 여행준비 등에도 많이 쓰일 것 같거든.

세 가지가 같은 모양이다. **어딘가를 정해두고, 왜 거기인지 적고, 나중에
그 자리를 다시 찾는 일.** 지금은 그것을 담을 자리가 없어 메모에 주소를
적어두는 수밖에 없고, 그러면 지도로 열 수도 없고 검색으로 찾기도 어렵다.

### 17-1.2 지도를 끼워 넣는 일은 나중에 한다

**1단계에서는 지도를 그리지 않는다.** 장소를 찾아 이름·주소·좌표까지
담고, 화면에는 지도 대신 **그 지도로 가는 링크**를 둔다.

까닭 셋이다.

- **새 열쇠도 도메인 등록도 없이 만들 수 있다.** 지도를 그리려면 구글은
  Maps Embed API 열쇠, 카카오는 JavaScript 열쇠가 따로 필요하고 둘 다
  도메인을 등록해야 한다. 이 저장소는 **도메인 등록을 빠뜨려 두 번 막혔다.**
  (`AGENTS.md` 6절, 12-A와 12-C)
- **이미 같은 방식을 쓰고 있다.** 영화·드라마의 `볼 수 있는 곳`이 그렇다.
  우리가 틀어주지 않고 갈 곳을 알려준다. (15절)
- **좌표를 담아두면 2단계가 얹기만 하는 일이 된다.** 담는 것과 보여주는
  것이 갈려 있어 1단계가 헛일이 되지 않는다.

**2단계에서 지도를 붙인다.** 열쇠를 받고 `localhost:3001`과 배포 주소를
**둘 다** 등록한 뒤에 한다. 되는지는 브라우저에서 눌러봐야 안다.
열쇠 이름은 그때 24절에 적는다. **쓰지 않는 환경변수를 미리 적지 않는다.**

### 17-1.3 찾는 곳과 보여주는 곳을 가른다

국내와 해외를 나누되, **나누는 자리가 둘이다.**

| | 국내 | 해외 |
| --- | --- | --- |
| **찾기** (이름 → 주소·좌표) | 카카오 Local | 구글 |
| **찾기** (주소 → 좌표·우편번호) | 카카오 Local | 구글 |
| **보여주기** (2단계) | 카카오 | 구글 |

#### 이름으로 찾기와 주소로 찾기를 둘 다 둔다 (2026-09-25에 더함, 사용자 요청)

> 혹시 상호명이나 이름이 부정확한 경우에는 지도에서 직접 찾아서 등록하게
> 하는 것도 방법일 것 같아.

**진짜 지도에서 찍어 고르는 것은 2단계다.** 지도를 그려야 하고, 그러려면
JavaScript 열쇠와 도메인 등록이 먼저다.

그런데 그 요청의 속뜻은 "이름이 틀렸을 때도 담을 수 있게 하라"이고, **그것은
지금 할 수 있다.** 이름이 부정확해도 **어디쯤인지는 보통 안다.** 카카오에
주소로 묻는 길이 따로 있고(`/v2/local/search/address.json`) 같은 REST 열쇠로
된다. 도메인 등록도 필요 없다.

| | 이름으로 찾기 | 주소로 찾기 |
| --- | --- | --- |
| 무엇으로 묻나 | 상호명 | 도로명·지번 주소 |
| 우편번호 | **없다** | **있다** (`zone_no`) |
| 장소 번호 | 있다 (`id`) | 없다 |
| 이름이 틀렸을 때 | 못 찾는다 | **찾는다** |
| 자료 제목을 바꾸나 | 바꾼다 | **안 바꾼다** |

마지막 줄이 중요하다. **주소로 찾을 때는 제목을 건드리지 않는다.** 주소로
찾는 상황은 곧 "내가 적은 이름이 카카오에 없다"는 상황이고, 그때 카카오가
아는 이름으로 덮으면 **사용자가 부르던 이름을 우리가 지우는 것**이 된다.
주소로 찾기는 좌표·우편번호·주소만 채운다.

**카카오로 시작한다.** 이미 `KAKAO_REST_API_KEY`로 책을 찾고 있고,
`EXTERNAL_PROCESSORS`에도 이미 적혀 있다. 계정도 열쇠도 방침도 늘지 않는다.
카카오 Local의 키워드 검색이 같은 REST 열쇠로 되는지는 **눌러봐야 안다.**

구글 지도는 **한국에서 유독 부실하다.** 지도 데이터 반출 규제 때문에
길찾기가 안 되고 상세도가 떨어진다. 국내를 구글로 덮으려 하지 않는다.

해외 검색은 **1단계에 넣지 않는다.** 국내부터 쓰면서 무엇이 모자란지
본 뒤에 정한다. 그동안 해외 장소는 이름과 주소를 직접 적을 수 있다.
**밖에서 못 찾아와도 우리 기능이 멈추지 않는다.** (15-E의 판단과 같다)

| 칸 | 뜻 |
| --- | --- |
| `visit_status` | **비워둘 수 있다.** 안 정함 / 가보고 싶다 / 가봤다 |

#### `category`에 무엇을 담는가 (2026-09-25에 고침)

처음에는 `음식점`, `관광명소` 같은 짧은 말을 담기로 적었다. 카카오의
`category_group_name`이다. **눌러보니 그 칸이 자주 비어 있었다.**
`경복궁`으로 물은 열다섯 건 중 **아홉 건이 빈 글자**였다.

| 장소 | `category_group_name` | `category_name` |
| --- | --- | --- |
| 경복궁 | `관광명소` | 여행 > 관광,명소 > 문화유적 > 고궁,궁 |
| 경복궁식당 | `음식점` | 음식점 > 한식 |
| **경복궁 근정전** | **(빈 글자)** | 여행 > 관광,명소 > 문화유적 |
| **경복궁 경회루** | **(빈 글자)** | 여행 > 관광,명소 > 문화유적 |

**하필 궁 안의 건물들이 분류 없이 온다.** 답사지로 담을 만한 것들이 그렇다.
그대로 만들면 `관광명소`로 걸러볼 때 근정전도 경회루도 나오지 않고,
**오류는 나지 않는다.** 사용자는 그런 것을 담은 적이 없다고 생각한다.

그래서 `category_name`을 **통째로** 담는다. `음식점 > 한식 > 한정식`처럼
온다. 이쪽은 늘 채워져 온다.

- **찾을 수 있는 말이 늘어난다.** `음식점`만 담으면 `한식`으로 못 찾는다.
  길을 통째로 담으면 `음식점`·`한식`·`한정식` 모두 걸린다.
- **화면에는 마지막 토막만 보여준다.** `고궁,궁`, `한식`. 담는 것과
  보여주는 것을 가른 자리다.
- **칸을 둘로 늘리지 않는다.** `category_group_name`을 따로 두면 같은 뜻의
  칸이 두 벌이 되고, 화면이 어느 쪽을 보아야 할지 알 수 없어진다.
  게다가 절반 넘게 비는 값으로 거르는 기능은 **조용히 반을 빠뜨린다.**

#### 우편번호는 이름으로 찾을 때 오지 않는다 (2026-09-25에 더함, 사용자 요청)

> 우편 주소는 다섯자리를 말하는게 맞아.

**이름으로 찾는 응답에는 우편번호가 없다.** 문서로 확인했다. 주소로 찾는
응답에만 `road_address.zone_no`로 들어 있다. 그래서 우편번호를 담으려면
주소로 찾기가 함께 있어야 한다. 두 기능이 한 덩어리인 까닭이 이것이다.

**모양을 다섯 자리로 못박지 않는다.** 국내 우편번호는 2015년부터 다섯
자리지만, 해외 장소는 손으로 적고 **거기에는 글자가 섞인다.**
영국의 `SW1A 1AA`가 그렇다. 다섯 자리만 받으면 해외 장소의 우편번호를
담을 수 없고, 그러면 "밖에서 못 찾아와도 우리 기능이 멈추지 않는다"는
17-1.3절의 판단과 어긋난다.

대신 길이만 짧게 잡고 빈 글자를 막는다. 우편번호로 셈을 하는 곳은 없다.
보여주고 찾는 값이다.

#### 빈 글자를 받지 않는다 (2026-09-25에 더함)

`road_address_name`이 **`null`이 아니라 빈 글자로** 온다. 열다섯 건 중 둘이
그랬다(별빛야행, 경회루). 그대로 담으면 화면은 `주소가 있다`고 판단하면서
아무것도 보여주지 못한다. **빈 줄만 뜬다.**

그래서 글 칸들에 `null이거나 빈 글자가 아니다`를 건다. 빈 장르 이름을
막아둔 것과 같은 방식이다. (15-E-2c-1, 검사 112)

#### `x`가 경도, `y`가 위도다

카카오는 좌표를 `x`·`y`로 준다. **뒤바꿔 넣으면 위도 칸에 126이 들어간다.**
제약조건이 막고 검사 124가 그것을 본다. 안 막으면 지도 링크가 바다
한가운데를 열고, 사용자는 우리가 장소를 잃었다고 생각한다.

#### 고르는 목록에는 분류와 주소를 함께 보여준다

`경복궁`으로 물으면 **549건**이 온다. 그 안에 `다이소 경복궁역점`,
`온유어마크 경복궁`이 섞여 있다. **이름만 보여주면 어느 것이 진짜 경복궁인지
고를 수 없다.** 한 번에 오는 것은 열다섯 건이다.

### 17-1.5 정하는 것들

- **장소 이름은 `sources.title`에 넣는다.** 따로 칸을 만들지 않는다.
  음악에서 곡 이름을 `sources.title`과 합친 것과 같다. **같은 뜻의 칸이
  두 벌이 되면 한쪽이 저장되지 않는다.** (15-E에서 겪음)
- **왜 담았는지는 `sources.description`.** 그곳에서 떠오른 생각은
  **기록(Capture)**이다. 새 칸을 만들지 않는다.
- **`visit_status`는 옵션이다.** (2026-09-25, 사용자가 정함) 여행 준비에는
  `가보고 싶다`와 `가봤다`가 갈리지만 수업 준비에는 그 구분이 쓸모없을 수
  있다. 안 정하면 화면에 아무것도 보이지 않는다.

  값이 셋인 까닭이 이것이다. **비어 있는 것과 `가보고 싶다`는 다르다.**
  둘로만 두면 안 정한 것이 `가보고 싶다`로 보인다. (15-E-2c-2b에서
  "비어 있는 것과 1은 다르다"를 겪었다)
- **영업시간, 평점, 사진은 담지 않는다.** 밖에서 받아와도 **금방 낡고,
  낡은 값이 맞는 값처럼 보인다.** 필요하면 `place_url`로 보낸다.
- **좌표에 범위 제약을 건다.** 위도 -90~90, 경도 -180~180. 밖에서 받아온
  값이 그대로 들어오는 자리다.
- **Capture에 위치 정보를 두지 않는다.** PDF의 쪽, 영상의 시점 같은 것이
  장소에는 없다. 필요해지면 그때 만든다. (`AGENTS.md` 2절 "쓰지 않을 값을
  미리 넣지 않는다")

### 17-1.6 표를 만들 때 함께 고칠 곳

`AGENTS.md` 7절의 네 곳에 **하나가 더 붙는다.**

1. `003_rls_isolation_test.sql`에 격리 검사 — 막는 것과 여는 것 모두
2. `tests/migration-invariants.test.mjs`의 `PROTECTED_TABLES`
3. 003 결과 표의 세는 칸
4. `src/lib/account/export-tables.ts`의 `EXPORTED_TABLES`
5. **`src/lib/ai/profile-search.ts`의 `PROFILE_SEARCH_TARGETS`** —
   안 넣으면 **주소나 분류로 찾을 수 없다.** 2026-09-25에 딸린 정보 표가
   통째로 검색 밖에 있던 것을 사용자가 찾았고, 그때 만든 목록이다.

### 17-1.7 경로

**새 경로를 만들지 않는다.** (2026-09-25에 고침)

처음에는 `/library/places`를 만들기로 적었다. 21절 목록에 `/library/books`,
`/library/music`처럼 매체마다 경로가 하나씩 적혀 있어서 그 줄을 따랐다.

**실제로 만들어진 것은 `/library/papers` 하나뿐이다.** 나머지는 모두
`/library?type=...`으로 걸러 본다. 그 덕에 정렬·별·태그·보기 방식이 한
화면에 모여 있고, 매체가 늘어도 그 기능들을 다시 만들지 않는다.

장소만 따로 경로를 만들면 **같은 종류의 일이 화면마다 다르게 보인다.**
거기서는 태그로 거를 수 없고, 별만 모아 볼 수도 없다. 그러려면 그 기능들을
한 벌 더 만들어야 한다.

그래서 담아둔 장소는 `/library?type=place`에서 본다. `SOURCE_TYPES`에
`place`를 더하면 저절로 생긴다.

21절의 경로 목록은 **만들려던 것이고 만들어진 것이 아니다.** 그 줄을 근거로
새 경로를 만들지 않는다.

## 17-2. 앱 안에 지도 그리기 (2026-09-25)

1단계에서 좌표까지 담고 지도는 그리지 않았다. (17-1.2절) 그 판단은
**담는 것과 보여주는 것을 갈라 두면 2단계가 얹기만 하는 일이 된다**는
것이었고, 이 절이 그 얹는 일이다.

**그 판단이 맞았다.** 표도 화면도 고치지 않았다. 담아둔 좌표를 읽어
지도를 그리는 칸 하나를 주소 아래에 얹었을 뿐이다. 마이그레이션이 없다.

### 17-2.1 어디에 그리나 (사용자가 정함)

> 지도를 그릴 화면은 저장된 장소 기록에 놔야지 (주소나 이런 정보들
> 아랫쪽에 말이야)

자료 상세의 **장소 칸 안**, 주소·좌표 칸 **아래**다. 새 화면을 만들지 않는다.

그 자리인 까닭. **지도는 주소를 확인하는 수단이다.** 찾아 고른 주소가 맞는
곳인지는 글자로 봐서는 알 수 없고 지도를 봐야 안다. 그러니 주소 바로 아래가
맞는 자리다. 멀리 두면 눈을 두 번 옮겨야 한다.

**목록에 여러 장소를 한 지도에 찍는 것은 하지 않는다.** 그것은 다른 기능이다
(답사 동선 짜기, 여행 경로 보기). 필요해지면 그때 정한다.
(`AGENTS.md` 2절 "쓰지 않을 값을 미리 넣지 않는다"와 같은 생각이다)

**좌표가 없는 장소에는 그리지 않는다.** 그릴 것이 없다. 그 자리에는 지금처럼
"좌표를 채우면 지도가 보입니다"를 둔다. 빈 상자를 그리면 고장처럼 보인다.

### 17-2.2 링크는 지도 아래에 남긴다 (사용자가 정함)

> 세번째 내용은 링크로 가는 것도 지도 아랫쪽에 유지시켜주었으면 해.

지도가 생겨도 카카오맵·구글 지도 링크를 없애지 않는다. **지도 아래로
내려 둔다.**

까닭이 있다. 우리가 그리는 지도로는 **할 수 없는 일이 있다.**

| 우리 지도 | 그쪽 지도·앱 |
| --- | --- |
| 어디인지 보여준다 | 보여준다 |
| — | **길찾기** |
| — | **휴대폰 지도 앱으로 열기** |
| — | 거리뷰, 리뷰, 영업시간 |

답사지를 담는 사람이 마지막에 하는 일은 **거기까지 가는 것**이다. 그 일을
우리가 할 수 없으므로 길을 남긴다. 영화·드라마의 `볼 수 있는 곳`과 같다.
우리가 틀어주지 않고 갈 곳을 알려준다. (15절)

### 17-2.3 JavaScript 열쇠는 브라우저로 나간다

**이것이 이 절에서 가장 중요한 부분이다.** 지금까지의 열쇠와 다루는 방식이
다르다.

| | REST 키 (지금) | JavaScript 키 (2단계) |
| --- | --- | --- |
| 어디서 쓰나 | **서버** | **브라우저** |
| 사람이 볼 수 있나 | 아니다 | **볼 수 있다** |
| 무엇이 지키나 | 서버 밖으로 안 나감 | **도메인 등록** |

지도는 브라우저가 그린다. 그러니 열쇠가 화면 소스에 실려 나간다.
**그것은 고장이 아니라 그 열쇠의 설계다.** 감출 수 없다.

그러면 무엇이 막아주는가. **카카오에 등록한 도메인뿐이다.** 카카오가
"이 열쇠는 등록된 주소에서 온 요청만 받는다"로 지킨다. 남이 열쇠를 베껴
가도 자기 사이트에서는 지도가 안 뜬다.

그래서 **도메인 등록이 선택이 아니라 유일한 방어선이다.** 1단계에서는
REST 쪽이라 등록이 필요 없었고 그래서 하지 않았다. 여기서는 다르다.

이 저장소의 규칙 하나와 부딪히는 것처럼 보인다. "비밀값을 브라우저 코드에
노출하지 않는다"(12절)가 그것이다. **부딪히지 않는다. 이 열쇠는 비밀값이
아니다.** 다만 그 사정을 적어두지 않으면 둘 중 하나가 일어난다. 다음에
보는 사람이 열쇠가 새고 있다고 여기거나, 반대로 **REST 키도 같은 식으로
내보내도 된다고 오해한다.** 뒤엣것이 더 위험하다.

열쇠 이름은 `NEXT_PUBLIC_KAKAO_JAVASCRIPT_KEY`다. 브라우저로 나가는 값이라
`NEXT_PUBLIC_`으로 시작해야 한다. 24절과 `.env.example`에 적었다.

**환경변수를 변수로 빼서 읽지 않는다.** `process.env.NEXT_PUBLIC_...`을
글자 그대로 적어야 Next.js가 빌드할 때 값을 박아 넣는다. 변수로 빼면
브라우저에서 `undefined`가 되고 **오류 없이 지도만 안 뜬다.**

박혔는지 확인하는 법. `npm run build` 뒤에 브라우저 묶음에서
`NEXT_PUBLIC_KAKAO_JAVASCRIPT_KEY`라는 **글자를 찾는다. 없어야 맞다.**
있으면 값으로 바뀌지 않은 것이다. 2026-09-25에 그렇게 확인했다.

### 17-2.4 방침이 달라진다

지금은 **우리 서버가** 카카오에 물어본다. 이용자 브라우저는 카카오에
닿지 않는다.

지도를 그리면 **이용자 브라우저가 카카오에 직접 접속한다.** 지도 타일
그림을 받아와야 하기 때문이다. 그러면 카카오가 **이용자의 IP와 접속
기록을 직접** 받게 된다. 우리를 거치지 않는다.

**이것은 방침에 적어야 할 변화다.** `EXTERNAL_PROCESSORS`의 Kakao 항목이
지금은 "찾으려는 책 제목, 장소 이름"을 보낸다고 적혀 있는데, 거기에
**브라우저가 직접 접속한다는 사실**이 더해져야 한다. 보내는 값이 늘어난
것이 아니라 **보내는 주체가 달라진 것**이고, 개인정보 관점에서는 그쪽이
더 큰 변화다.

같은 커밋에서 고친다. (`AGENTS.md` 2절)

### 17-2.5 지도가 안 떠도 멈추지 않는다

세 가지 경우에 지도가 안 뜬다.

- 열쇠가 없다 (환경변수 미설정)
- 도메인이 등록되지 않았다
- 브라우저가 밖의 스크립트를 막는다

**어느 경우에도 장소 기능은 그대로 돌아야 한다.** 주소는 보이고 링크는
눌린다. 지도 자리에만 "지금은 지도를 보여드리지 못합니다"가 뜬다.

**빈 상자를 그리지 않는다.** 이 저장소가 도메인 등록을 빠뜨려 두 번 막혔고
(12-A, 12-C) 그때마다 화면은 아무 말도 하지 않았다. 세 번째는 그러지 않는다.

## 17-3. 국내와 해외를 갈라 담기, 지도에서 찍어 담기 (2026-09-25, 사용자 요청)

> 해외의 경우에는 검색해도 안나와. (…) 애초부터 국내와 해외를 선택해서
> 등록시키는게 낫겠어.

> 이름을 기억하지 못하는 경우 거꾸로 지도에서 장소를 찾아서 등록시키는거는
> 아직 안된 것 같아. "지도에서 등록" 기능을 만들어서 (…)

### 17-3.1 갈라야 하는 까닭

1단계는 **국내만 찾고 해외는 손으로 적는다**로 정했다. (17-1.3절) 그
판단의 절반이 틀렸다. 손으로 적을 수 있게 해둔 것은 맞지만, **화면이
그것을 말해주지 않았다.** 해외 장소를 찾으면 `찾은 장소가 없습니다`만
뜨고, 그것이 "카카오에 없다"인지 "이름을 잘못 적었다"인지 알 수 없었다.

그래서 **담기 시작할 때 국내인지 해외인지 고르게 한다.** 고른 뒤에는
그쪽에 맞는 길만 보여준다. 없는 길을 눌러보고 나서야 없다는 것을 알게
하지 않는다.

**이것은 화면 상태가 아니라 장소의 성질이다.** 경복궁은 국내이고 에펠탑은
해외다. 나중에 그 장소를 다시 열 때도 같은 쪽이어야 하므로 **표에 담는다.**

좌표로 짐작하지 않는다. 위도·경도로 한반도 안인지 재는 방법이 있지만,
**좌표가 없는 장소에서는 알 수 없고** 국경 근처에서 틀린다. 무엇보다
사용자가 이미 말해준 것을 우리가 다시 추측하는 것은 뒤집힌 일이다.

### 17-3.2 `region`

| 값 | 뜻 |
| --- | --- |
| `domestic` | 국내. 카카오로 찾고 카카오맵을 그린다 |
| `overseas` | 해외 |

**비워둘 수 없다.** `visit_status`와 다르다. 가봤는지는 "안 정함"이 뜻을
가지지만, 장소가 국내인지 해외인지는 **안 정한 상태가 없다.** 담는 순간
어느 쪽인지 정해져 있다.

기본값은 `domestic`이다. 이미 담아둔 장소가 있고 그것이 국내이며, 앞으로도
국내가 더 많다.

### 17-3.3 지도에서 찍어 담기

이름을 기억하지 못할 때 쓰는 길이다. **이름으로 찾기와 주소로 찾기가
둘 다 막히는 경우**가 있다.

- 간판 이름과 등록된 상호가 다르다
- 이름은 잊었고 "그 골목 그 자리"만 기억난다
- 주소도 모른다

`지도에서 찍기`를 누르면 창이 떠서 지도가 나오고, 찍은 자리가 곧 그
장소가 된다. 찍고 `이 자리로 담기`를 누르면 창이 닫히고 칸이 채워진다.

**찍은 좌표를 주소로 바꾼다.** 카카오에 `coord2address`가 있고 **지금 쓰는
REST 열쇠로 된다.** 도로명 주소·지번 주소·우편번호를 함께 준다. 그래서
찍기만 하면 주소가 채워진다.

**이름은 채우지 않는다.** 지도는 이름을 모른다. 그 자리에 무엇이 있는지는
사용자가 적는다. 이름을 모를 때 쓰는 길이므로 그것이 맞다.

**창으로 띄우는 까닭.** 지도를 찍는 일에는 넓은 자리가 필요하고, 그동안
아래의 입력 칸들은 볼 일이 없다. 칸 안에 지도를 하나 더 그리면 화면이
길어져 무엇을 하는 중인지 알기 어려워진다. `띄워놓고 찾기`(16-A)와 같은
판단이다.

**찍기 전에는 담을 수 없다.** 창을 열자마자 `담기`가 눌리면 지도 가운데의
아무 자리가 담긴다.

### 17-3.4 해외를 무엇으로 찾을지는 아직 정하지 않았다

**여기에 값과 계정이 걸려 있어서 사용자가 정한다.**

카카오는 해외를 다루지 않는다. `coord2address` 문서도 국내 지명만 말한다.
그래서 해외에는 다른 수단이 필요하고, 고를 것이 셋이다.

| | 구글 지도 | OpenStreetMap | 카카오맵으로 좌표만 |
| --- | --- | --- | --- |
| 자료 품질 | **가장 좋다** | 이름난 곳은 괜찮다 | 해외는 부실하다 |
| 새 열쇠 | 필요 | **필요 없다** | **필요 없다** |
| 결제 계정 | **필요하다** | 필요 없다 | 필요 없다 |
| 새 라이브러리 | 없다 | **필요하다** (Leaflet) | 없다 |
| 주소 받아오기 | 된다 | 된다 | **안 된다** (손으로) |

구글은 **프로덕션에서 결제 계정이 필수다.** 문서에 적혀 있다. 무료 크레딧이
있어도 카드를 걸어야 한다. 그것은 우리가 정할 일이 아니다.

정해지면 이 절에 적고 만든다. **정해지기 전까지 해외는 손으로 적는다.**
이름·주소·좌표를 직접 넣을 수 있고, 구글 지도 링크로 열린다. 그래서
해외 장소를 **담을 수는 있다.** 찾아주지 못할 뿐이다.
(15-E의 "밖에서 못 찾아와도 우리 기능이 멈추지 않는다"와 같은 자리다)

## 19-E. 유저별 과금 기능 사용량과 허용량 (2026-09-25, 사용자 요청)

> 유저 관리에 유저별로 AI 기능이나 이런 과금과 관련된 제한이 걸린 서비스의
> 이용 횟수를 조회하게 해주는 것도 좋을 것 같아.

> 유저별로 요청이 들어오거나 내가 판단해서 사용량 리셋을 할 수 있게

### 19-E.1 "리셋"이 아니라 "허용량 더하기"다

**요청은 리셋이었다. 그대로 만들면 안 된다.**

`ai_usage_events`는 **고칠 수도 지울 수도 없는 장부**다. 003의 검사 120과
121이 그것을 지킨다.

> 고칠 수 있는 장부는 장부가 아니다. 글자 수를 0으로 바꾸면 한도가 비켜 간다.
> 지울 수 있으면 한도에 걸린 사람이 장부를 비우고 다시 쓰면 그만이다.

리셋을 만들면 **그 보장을 우리 손으로 뚫는 일**이 된다. 관리자만 할 수
있게 해도 마찬가지다. 뚫린 길은 언젠가 쓰인다.

그래서 **장부는 그대로 두고 허용량을 더한다.**

| | 리셋 | **허용량 더하기** |
| --- | --- | --- |
| 장부 | 지워진다 | 그대로 남는다 |
| 누가 얼마 썼는지 | 알 수 없게 된다 | **영원히 남는다** |
| 왜 풀어줬는지 | 안 남는다 | **기록에 남는다** |
| 되돌리기 | 안 된다 | 된다 |

**관리자가 보는 결과는 같다.** 단추를 누르면 그 사람이 다시 쓴다.
다만 장부가 거짓말을 하지 않는다.

한도를 셀 때 이렇게 본다.

```
쓸 수 있는 횟수 = 기본 한도 + 이번 달에 더해준 허용량
남은 횟수      = 쓸 수 있는 횟수 − 이번 달에 쓴 횟수
```

### 19-E.2 `ai_usage_grants`

| 칸 | 뜻 |
| --- | --- |
| `owner_id` | **허용량을 받는 사람.** `auth.uid()`가 아니다 |
| `granted_by` | 누가 더해줬는지. 트리거가 채운다 |
| `extra_calls` | 몇 번 더 |
| `reason` | 왜. **비울 수 없다** |
| `created_at` | 어느 달의 허용량인지를 이 값으로 가른다 |

**`owner_id`에 `default auth.uid()`를 걸지 않는다.** 이 저장소의 다른 표와
정반대다. 다른 표들은 "내 것을 내가 만든다"이고, 여기는 **관리자가 남의
줄을 만든다.** 기본값을 걸면 관리자 자신에게 허용량이 붙는다.

그래서 생성된 타입도 `owner_id`를 필수로 본다. **그것이 맞다.** 누구에게
주는지는 반드시 적어야 하는 값이다.

**`reason`을 비울 수 없게 한다.** 까닭 없이 풀어준 기록은 나중에 읽을 수
없다. "왜 이 사람만 200번을 썼나"에 답하지 못한다. 그 답을 만들려고 이
표가 있는 것이다.

**고칠 수도 지울 수도 없다.** 장부와 같다. 잘못 줬으면 **음수로 한 줄 더
남긴다.** 지우는 것이 아니라 되돌린 기록을 남기는 것이다.

### 19-E.3 누가 무엇을 할 수 있나

| | 읽기 | 넣기 | 고치기·지우기 |
| --- | --- | --- | --- |
| 본인 | **자기 것만** | 안 됨 | 안 됨 |
| 관리자 | 전부 | **됨** | 안 됨 |

본인이 자기 허용량을 볼 수 있어야 하는 까닭. 화면이 `60번 중 3번 남음`을
보여주는데, 허용량을 못 읽으면 **관리자가 풀어준 뒤에도 그 숫자가 안 바뀐다.**
사용자는 왜 되는지 모르고 쓴다.

`admin_audit_logs`에도 남긴다. 관리자가 한 일은 전부 그 표에 남는 것이
이 저장소의 규칙이다.

### 19-E.4 유저별 사용량 조회

관리자 화면(`/admin/users`)에 사람마다 이번 달 사용량을 보여준다.

**`service_role`로 읽지 않는다.** 이 저장소가 한 번 빠진 자리다. (17-A)
관리자가 남의 장부를 읽는 일은 RLS 정책으로 열면 된다. **우회할 곳이 늘어나면
지키는 곳이 줄어든다.**

보여줄 것.

| | |
| --- | --- |
| 이번 달 부른 횟수 | 갈래별로 나눠 본다. 번역·검색·자리 추천 |
| 이번 달 허용량 | 누가 언제 왜 더해줬는지 |
| 남은 횟수 | 기본 한도 + 허용량 − 쓴 횟수 |

**갈래를 나눠 보여주는 까닭.** 장부가 답해야 할 물음이 "얼마나 썼는가"
하나가 아니라 **"왜 이 달에 많이 나왔는가"**이기도 하다. 19-D에서 갈래를
나눈 것과 같은 이유다.

### 19-E.5 구글 지도도 같은 자리에 온다

해외 지도·검색이 붙으면 그것도 과금되는 기능이다. 다만 **세는 자리가
다르다.** AI는 우리 서버가 부르므로 장부에 남길 수 있는데, 지도는
**이용자 브라우저가 직접 부른다.** 우리가 셀 수 없다.

그래서 구글 쪽은 **Google Cloud의 하루 상한**으로 막는다. (17-3.4절)
31일 내내 상한까지 써도 무료 한도를 넘지 않는 숫자로 잡으면 과금이 수학적으로
불가능하다. **우리 장부에 넣을 수 없는 것을 넣은 척하지 않는다.**

| API | 하루 상한 | 최대 월 사용 | 월 무료 |
| --- | --- | --- | --- |
| Maps JavaScript | 300 | 9,300 | 10,000 |
| Places (New) | 150 | 4,650 | 5,000 |
| Geocoding | 100 | 3,100 | 10,000 |

## 18. 외부 API와 메타데이터

초기 또는 단계별로 사용할 수 있는 공급자:

- Crossref: DOI 기반 논문 메타데이터
- OpenAlex: 논문·저자·인용 관계 보완
- KCI/RISS/Google Scholar: 우선 검색 바로가기
- Kakao Book Search: 도서와 표지
- Kakao Local: 장소 이름으로 주소와 좌표 (17-1절). 같은 REST 열쇠를 쓸 수
  있는지는 눌러봐야 안다
- MusicBrainz: 곡·아티스트·앨범·ISRC 등 음악 메타데이터
- Cover Art Archive: MusicBrainz release 기반 앨범 표지
- Spotify·Apple Music: 선택적 메타데이터·공식 재생 링크 또는 embed
- YouTube Data API: 영상 메타데이터
- TMDB: 영화·TV·포스터·watch providers
- 생성형 AI 또는 번역 API: 부분 번역, 요약, 임베딩

외부 API 응답은 신뢰 가능한 사용자 입력으로 취급하지 않는다. Zod로 검증하고 오류·누락에 대비한다. 외부 API가 중단되어도 기존 Source와 Capture를 열 수 있어야 한다.

### 18.1 생성형 AI 공급자와 비용 정책

ThreadMark의 생성형 AI 공급자는 **Anthropic Claude API**로 결정한다.

- Anthropic Console에 ThreadMark 전용 Workspace를 생성했다.
- Workspace 월 예산 상한은 **USD 5**로 설정했다.
- ThreadMark 서버 전용 API 키를 생성했다.
- 기본 모델은 `claude-sonnet-5`로 사용한다.
- 비용 절감이 중요한 짧은 분류·태그 후보 생성에는 `claude-haiku-4-5-20251001` 사용을 선택적으로 검토한다.
- Claude API 키는 Next.js 서버 전용 환경변수에만 저장하고 브라우저 코드, 로그, Git 저장소에 노출하지 않는다.
- 초기 환경변수 이름은 `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `ANTHROPIC_BUDGET_USD`로 통일한다.
- `ANTHROPIC_MODEL`의 초기값은 `claude-sonnet-5`, `ANTHROPIC_BUDGET_USD`의 초기값은 `5`로 둔다.

초기 적용 범위:

- 사용자가 직접 선택한 PDF 또는 Capture 텍스트의 부분 번역
- 짧은 요약
- 키워드와 태그 후보
- 연구·수업 활용 아이디어 초안

데이터 전송 원칙:

- 사용자가 명시적으로 실행한 범위만 Claude API로 전송한다.
- PDF 전체나 Google Drive 파일 전체를 자동 전송하지 않는다.
- 요청 전에 전송될 텍스트 범위를 사용자가 확인할 수 있게 한다.
- AI 결과는 원문, 사용자 작성 내용과 구분하고 모델명과 생성 시점을 기록할 수 있게 한다.
- 예산 상한에 가까워지거나 초과하면 AI 요청을 중단하고 사용자에게 안내한다.

Claude는 자체 임베딩 모델을 제공하지 않으므로 의미 검색용 임베딩 공급자는 MVP 이후 별도로 결정한다. 초기 MVP에서는 Claude 텍스트 생성 기능과 일반 키워드 검색을 우선하며, 임베딩 공급자나 로컬 임베딩 모델을 성급하게 추가하지 않는다.

### 18.1-1 AI에게 물어보기를 붙이며 (2026-09-25, 16-A)

19절의 AI 검색을 만들며 이 절과 맞춘 것을 적어 둔다.

- **임베딩을 붙이지 않았다.** 위 문단이 이미 그렇게 정해 두었고, 확인해 보니
  Anthropic에 임베딩 API가 없는 것도 그대로였다. 19절의 흐름 중 벡터 검색만
  빼고 `키워드 검색 → 관련 Capture 선별 → AI가 관계 설명`으로 만들었다.

- **모델은 `claude-sonnet-5`를 그대로 쓴다.** 만드는 동안 `claude-opus-5`를
  기본으로 두려고 했다. 흩어진 기록을 놓고 관계를 말하는 일이라 값싼 모델은
  그럴듯하지만 틀린 연결을 만들고, 번역과 달리 견줄 원본이 없어 알아채기
  어렵기 때문이다.

  **그러나 이 절이 월 예산 상한을 USD 5로 정해 두었다.** 그 상한은 Anthropic
  쪽에 걸려 있어 넘으면 우리 코드와 상관없이 요청이 거부된다. 더 좋은 모델을
  쓰면 같은 돈으로 물어볼 수 있는 횟수가 3분의 1로 준다. 문서가 최우선
  기준이므로 문서를 따랐다.

- **환경변수 `ANTHROPIC_SEARCH_MODEL`을 더했다.** 이 절이 이름을 셋으로
  통일한다고 했으므로 늘린 까닭을 적는다.

  비어 있으면 `ANTHROPIC_MODEL`을 쓰고, 그것도 없으면 `claude-sonnet-5`다.
  **지금은 아무것도 달라지지 않는다.** 갈라둔 자리를 미리 만든 것이며,
  이 절이 "짧은 분류·태그 후보 생성에는 haiku를 검토한다"고 한 그 상황에서
  필요해진다. 번역을 haiku로 내릴 때 물어보기까지 함께 내려가면 곤란하다.

  올릴 때는 **Anthropic Console의 예산과 앱의 월 한도를 함께** 본다.
  한쪽만 고치면 예산에 먼저 걸려 기능이 통째로 멈춘다.

- **앱의 월 한도는 예산에서 거꾸로 셈했다.** `src/lib/ai/limits.ts`에 셈을
  적었다. 한 번에 $0.065 어름이고 USD 5면 일흔 번 남짓인데, 번역도 같은
  예산을 쓰므로 60으로 두었다. **막는 자리가 둘일 때는 안쪽이 먼저 걸려야
  한다.** 앱이 먼저 막으면 "이번 달 다 쓰셨습니다"가 나오고, Anthropic이
  먼저 막으면 기능이 그냥 고장 난 것처럼 보인다.

- **`/ai-search`는 이 목록에 처음부터 있던 경로다.** `/search`와 따로 둔

## 19. AI 검색과 추천

AI 검색은 MVP 핵심 CRUD가 안정된 뒤 추가한다.

흐름:


- 검색 결과에는 관련 Capture와 출처 위치를 표시한다.
- AI 사용량 제한과 비용 추적을 둔다.

### 20-1 태그 (2026-09-24 정함, 15-B)

이 목록에 `tags`와 `capture_tags`만 있었다. 구현하면서 정한 것을 적는다.

**`source_tags`를 더했다. 이 절이 문서 안의 다른 곳과 어긋나 있었다.**
11.1절은 웹사이트 자료의 등록 정보에 `태그`를 적어두었고, 13.5절은 음악의 개인
분류(`집중할 때`, `수업 준비` 같은 것)를 두고 "이 값들은 일반 Tag로 저장하며
고정 목록으로 제한하지 않는다"고 한다. 둘 다 **자료**에 붙는 태그다. 그런데 이
목록에는 자료와 태그를 잇는 표가 없었다. 목록이 빠뜨린 것으로 읽었다.

자료와 기록 **양쪽에 단다.** 5.2-1절의 별과 같은 이유다. 중요한 논문과 중요한
문장이 다른 것처럼, "이 논문은 수업 준비에 관한 것"과 "이 문장이 수업 준비에
쓸 만하다"는 다른 사실이다.

**`tags` 목록은 둘이 나눠 쓴다.** 자료용과 기록용을 따로 두면 `수업 준비`를 양쪽에
치게 되고, 그 태그로 모아 봐도 한쪽만 나온다. 태그를 다는 이유가 "흩어진 것을
한 이름으로 묶는 것"인데 그것이 되지 않는다.

**이름을 둘로 담는다.** `name`은 사람이 보는 그대로, `slug`는 같은 태그인지
판정하는 값이다. `slug`에 `unique(owner_id, slug)`를 건다.

`AI 융합수업`과 `ai 융합수업`과 ` AI  융합수업 `이 따로 쌓이면 고르는 줄에 비슷한
것이 셋 남는다. 어느 것을 눌러야 할지 알 수 없고, 하나를 누르면 나머지 둘에
달아둔 것이 안 보인다. 반대로 보이는 이름까지 소문자로 내려 담으면, `AI`를 쳤는데
화면에 `ai`로 나와 내가 친 것이 아닌 것 같아진다. 그래서 둘로 나눈다.

다듬는 규칙은 `src/lib/tags/name.ts` 한 곳에 있다. 유니코드 모양을 맞추고(NFC),
앞뒤 공백을 떼고, 가운데 이어진 공백을 하나로 줄이고, 소문자로 내린다.
**거기까지만 한다.** 공백을 아예 빼면 `수업 준비`와 `수업준비`가 하나가 되는데,
사용자가 다르게 쓸 뜻이었을 수 있다. 눈에 같아 보이는 것만 같다고 본다.

**고정 목록을 두지 않는다.** 13.5절이 그렇게 정하고 있다. 값은 사용자가 만든다.

**태그 이름은 고칠 수 있다.** 연결(`source_tags`, `capture_tags`)은 잇거나 끊는
것뿐이지만 `tags`에는 `UPDATE`를 준다. 오타를 고치려고 지웠다 다시 만들면
달아둔 것이 전부 끊긴다.

별(5.2-1절)과 역할이 겹치지 않는다. 별은 `다시 볼 것인가` 하나만 맡고, 태그는
`무엇에 대한 것인가`를 맡는다.

- `.env.example`에는 이름과 설명만 둔다.
- `.env.local`은 Git에서 제외한다.
- Vercel Preview와 Production 값을 분리한다.
- public prefix가 붙은 변수에는 공개되어도 되는 값만 둔다.
- **카카오 열쇠가 둘이고 다루는 방식이 다르다.** (2026-09-25, 17-2절)

  | | `KAKAO_REST_API_KEY` | `NEXT_PUBLIC_KAKAO_JAVASCRIPT_KEY` |
  | --- | --- | --- |
  | 쓰는 곳 | 서버 (책·장소 찾기) | 브라우저 (지도 그리기) |
  | 사람이 볼 수 있나 | 아니다 | **볼 수 있다** |
  | 무엇이 지키나 | 서버 밖으로 안 나감 | **카카오에 등록한 도메인** |

  뒤엣것은 화면 소스에 실려 나가고 **그것이 그 열쇠의 설계다.** 감출 수
  없다. 그래서 도메인 등록이 선택이 아니라 유일한 방어선이다.
  `localhost:3001`과 배포 주소를 **둘 다** 등록한다. (17-2.3절)

  **앞엣것을 지도에 쓰지 않는다.** 카카오 문서가 콕 집어 그러지 말라고
  적어두었고, 두 열쇠가 콘솔의 같은 화면에 나란히 있어 헷갈리기 쉽다.
- Supabase publishable key와 `threadmark-server` secret key 생성을 확인했으며, legacy `anon`·`service_role` 키 대신 사용한다.
- 로컬 `.env.local`에 필수 개발 환경변수와 별도 생성한 256-bit token 암호화 키를 입력했으며 Git 제외 상태를 확인했다.
- Vercel Production에 Config 9개와 Secret 8개를 프로젝트 범위로 등록하고 새 Production 배포에 적용했다.
- Preview에는 Supabase secret key, Google OAuth client secret, token 암호화 키 및 외부 API 비밀값을 기본 제공하지 않는다. Preview는 공개 설정과 RLS가 적용되는 Supabase publishable key만 사용하며, 필요한 서버 기능은 별도 Preview 자격 증명을 마련하기 전까지 비활성화한다.

## 25. 완료 기준과 테스트

### 핵심 통합 테스트

1. 사용자 A가 사용자 B의 Source, Capture, Project를 읽거나 수정할 수 없다.
2. Drive 미연결 사용자는 URL Source와 텍스트 Capture를 저장할 수 있다.
3. Drive 연결 사용자는 PDF를 업로드하고 다시 열 수 있다.
4. 텍스트 PDF에서 문장을 선택하면 페이지와 선택 문장이 함께 저장된다.
5. 저장된 Capture를 누르면 해당 페이지와 위치로 이동한다.
6. 선택 문장만 번역 API로 전송되고 전체 PDF는 전송되지 않는다.
7. Drive 권한을 취소해도 기존 Source와 Capture는 사라지지 않는다.
8. 사용자가 Drive 파일을 삭제하면 복구 가능한 오류 상태가 표시된다.
9. 모바일에서 PDF와 메모 탭을 전환할 수 있다.
10. MathLab의 Supabase 및 Vercel 환경에는 어떠한 변경도 발생하지 않는다.

## 28. 현재 결정 사항 요약

- 이름은 ThreadMark(TM)이다.
- 핵심 구조는 Source–Capture–Project다.
- GitHub 저장소는 public으로 운영하며 API·OAuth·암호화 관련 비밀값은 저장소에 커밋하지 않는다.
- 다중 사용자 구조와 RLS를 처음부터 적용한다.
- MathLab과 Supabase 프로젝트를 완전히 분리한다.
- 사용자 파일의 기본 저장소는 각 사용자의 Google Drive다.
- Google Drive는 `drive.file` 최소 권한과 Picker를 사용한다.
- 웹사이트는 URL, 메타데이터, 메모 및 선택 인용을 저장한다.
- 음악은 곡·앨범·공연 버전을 Source로 저장하고 재생 시점, 감상, 짧은 가사 구절 및 활용 아이디어를 Capture로 기록한다.
- 상업 음원과 전체 가사는 복제하지 않고 공식 링크·embed와 메타데이터를 사용한다.
- PDF.js로 텍스트 선택, 페이지 위치 저장 및 부분 번역을 지원한다.
- 텍스트 기반 공식 논문 PDF는 주요 기능이 대체로 작동하지만 예외에 대비한 fallback을 둔다.
- 논문 분석 템플릿과 프로젝트별 활용 계획을 제공한다.
- AI 의미 검색, OCR, 공유, 협업은 핵심 MVP 이후에 추가한다.
